### ✅ T1 · `writeBase64File` 接 `CasMode & BackupMode`（6 处调用点）— **已完成 2026-10-26**（记录见 §5.5）

**为什么排第一**：这 6 处写的是 `sj_ku*` / `sj_dz*` —— 用户导入的样式库、动作库，**唯一一份**。
现在覆盖前不比对、不看原文，坏了没有第二份。

**技术难点（必须在改之前定）**：

| 难点 | 现状 | 方案 |
|---|---|---|
| **CAS 比对的是字节，不是文本** | `compareSync` 用 `readTextSync` 读成字符串 | 新增 `compareBase64Sync(target, expectedBase64)`，用 `readBase64File` 取 `base64` 再比。字节的 base64 编码确定，可直接 `===` |
| **备份要写字节** | `backupOrQuarantine` → `writeBackupFile` → `writeTextFileAtomic`（文本） | `backupStep` 拆成 `backupTextStep` / `backupBytesStep`；字节版用 `atomicReplaceBytes` |
| **`.corrupt-*` 判据依赖文本** | `isUsableJsonText(previous)` 判"原文还算不算可用库文件" | `style-library-io.backupOriginal` 里已有一份**领域判据**（`isKuLibraryFileName` + `b64ToUtf8` + `isUsableJsonText`），**T1 只提供机制，判据仍留在 data 层**（传入 `quarantineOnCorrupt` 的回调？不 —— 见下） |

**⚠️ 这一条要在动手前拍板**：`quarantineOnCorrupt` 现在是「文本 + JSON 判据」，库文件的「坏」是**领域知识**（`b64ToUtf8` 解不出 / 不是库文件）。两种走法：

| 走法 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | `writeBase64File` 只接 `cas` / `backup: keep \| none`，**不做 quarantine 判定**；`style-library-io` 保留自己判「坏不坏」，判断结果用 `backup: 'none'` + 自己写 `.corrupt-*` | 仍有一份手写 `.bak`/`.corrupt`（T3 只能删一半） |
| **B** | 给 `DiskWriteOptions` 加 `quarantine?: (previousBytes: string) => boolean` 回调 | `disk-write` 开始知道"什么叫坏"，越权；且回调是第二个判据入口 |

### 5.17 那 5 处 `skip` 能不能改成真 CAS（2026-10-26 · 用户「继续」）

用户说继续 ⇒ 回头处理本横切最大的功能缺口：**5 处 `Repo.replace` 仍不比**（丢更新仍可能发生）。

**先查 `update` 能不能顶替**（它内部就是「读原文 → mutator → CAS 比对 → 冲突重读重跑」）：

```
rawUpdate（file-repo.ts:119-151）
  readRaw() → { read, text }        ← text = 磁盘原文
  if (!read.ok) throw               ← D-42：decode 失败就拒写
  next = mutator(read.value)
  persist(next, text, { compare, expected: text })   ← CAS 用的是**刚读的**原文
  CONFLICT → 重读 + 重跑 mutator（最多 retries 次）
```

**结论：不能顶替。** `replace` 与 `update` 的差别不是"谁更强"，是**语义不同**：

| | 读不到原文 | 原文坏（decode 失败） |
|---|---|---|
| `replace` | **抛**（`requireReadable`） | **照写**，坏原文隔离到 `.corrupt-*`（`quarantineOnCorrupt`） |
| `update` | 抛 | **抛**（D-42） |

`action-archive` 换 `update` ⇒ **「导入能修复坏索引」这个能力消失**（坏索引时不再照写 + 隔离，而是直接中止导入）。
我差点为了「看起来更完美」而破坏它，**停手**。

### 7.2 行为三问

**① 改前什么样、改后什么样（用户能看见的）**

| 场景 | 改前 | 改后 |

| 两个面板同时改偏好 | 后写静默覆盖，两边都显示「已保存」 | 后写抛 `CONFLICT`，提示「正被其他面板修改」，前一份保留 |

| 导入动作库覆盖同名库文件 | 覆盖，**没有 `.bak`** | 覆盖前写 `.bak` |
| 新装机写种子（常用页） | `Repo.write` 恒覆盖 | `expected: null` ⇒ 文件已存在就拒写，用户数据不被种子盖掉 |

### 7.3 这一轮真正修好的是什么

**不是「写盘代码变少了」（净增 300+ 行），是三件事从「靠人记得」变成「漏了就红」：**

1. **`cas` / `backup` 必填** ⇒ 14 个写入点漏表态**编译不过**（改前 13 处全在「没传」这一支）
2. **`Repo.write` + `overwrite` 合并** ⇒ 入口 7 → 6，种子写有了「必须不存在」的真 CAS
3. **`writeBase64File` 接选项** ⇒ 6 处库文件写从「零保护」变成「可选比对 + 可选备份」
