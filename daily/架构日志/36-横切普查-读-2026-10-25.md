## 二、三个角度的结论

### 角度 1 · 是否唯一

**实现层：真唯一（删掉 `src/cep/fs.ts` 剩 0 份）。**

- `grep -rln "readFileSync" src/` → **只有 `src/cep/fs.ts`**（`disk-write.ts` 只写不读）。
- 判据三件套各 **1 份**：`readNodeOutcome`（骨架）、`classifyFsError`（ENOENT 判据）、`combineReads`（合并策略）。
- 注释里写明"为什么必须只有一份"（`fs.ts:157-163`）：四份会各自漂移，一处把 `EPERM` 认成"没有"，就会「读不到 → 当成首次使用 → 拿默认值覆盖用户文件」（D-42 / T-105）。

**消费形状层：❌ 不唯一 —— 10 种读结果形状并存。**

| 形状 | 定义处 | 判别位 | 失败怎么表达 |
| --- | --- | --- | --- |
| `TextRead` | `cep/fs.ts:103` | `status: ok/notSeen/error` | `error` + `reason` ✅ |
| `Base64Read` | `cep/fs.ts:198` | `status` | 同上 ✅ |
| `RepoRead<T>` | `cep/data/types.ts:53` | `ok: true/false` | `RepoReadBad{reason, fallback}` ✅ |
| `SysFontRead` | `cep/data/sys-font.ts:29` | `status: ok/none/…` | 三态 ✅ |
| `LedgerRead` | `cloud/types.ts:39` | `status: ok/none/broken` | `broken` + `reason` ✅ |
| `FontStarsRead` | `cep/data/font-meta.ts:24` | **裸 `ok: boolean`** | **`stars: {}` 空表 ≠ "全未收藏"，靠注释提醒** ⚠️ |
| `KuIndexRead` | `domain/style-library.ts:55` | **裸 `degraded: string`** | **可忽略字段** ⚠️ |
| `KuLibraryRead` | `cep/data/style-library-repo.ts:51` | **裸 `note: string`** | **可忽略字段** ⚠️ |

消费侧判别位散落：`.ok` **45** 处 / `.status` **88** 处 / `.degraded` **14** 处。
**判别位有 4 种**（`ok` / `status` / `degraded` / `note`）——同一句「读到坏数据该怎么办」在 4 套语法里各写一遍。

### 角度 2 · 数据流是否清晰

**✅ 清晰，没被改写 / 猜 / 造。**

单点在 `cep/data/file-repo.ts:62-101`（`readRaw`）：

1. `readTextOutcome(target)` —— 只报观测，不下结论（ADR-26 ②）；
2. `classifyFsError` —— **唯一的错误归判据**，只认 `ENOENT` 是 `notSeen`，其余一律 `error` + 原始 `reason`；
3. `JSON.parse` —— 失败 `log.error` + `ok:false`，**不吞**；
4. `decode(parsed)` —— **必填参数**，"没有形状通道"这条路不存在（TD-03-5 / T-99-2）；`decode` 里**不许补默认值**，缺字段必须留痕（`utils/decode.ts` 文件头）；
5. 产出 `RepoRead<T>` —— 判别联合，`ok:false` 时类型上取不到 `.value`（T-101-2）。

**⚠️ 但有 3 条裸形状支路绕过了 `RepoRead` 的判别联合**（见上表 ⚠️ 行）：`FontStarsRead.ok: boolean`、`KuIndexRead.degraded: string`、`KuLibraryRead.note: string` —— 读失败 / 降级被压成**一个可忽略的字段**，正是 ADR-14「失败归一空值」的形态。

### 角度 3 · 结构上别人是否不可能绕过

**❌ 不可能绕过 = 不成立。分三层说：**

| 层 | 闸 | 在 check 链上？ | 实测 |
| --- | --- | --- | --- |
| 页面 → `@/cep/{jsx,data,events}` | eslint `no-restricted-imports`（`eslint.config.js:144-167`） | ✅ 在（`check` 第 4 步 `lint`） | 会红 |
| 页面 → `@/cep/fs`（读出口） | `scripts/page-boundary.mjs` 的 `READONLY_EXPORTS` / `WRITE_EXPORTS` | ❌ **不在** | **能红，但没人跑** |
| 命令层 / 数据层 → `@/cep/fs` | **无** | — | `commands/font.ts:262`、`commands/rename.ts:218` 直读，靠注释自辩（`font.ts:265-268`） |

**负例探针（真跑，文件已还原）**：往 `src/pages/style/index.vue` 塞 `import { readTextOutcome } from '@/cep/fs'` **并真用上它**（`void readTextOutcome`）：

| 命令 | 结果 |
| --- | --- |
| `npm run lint` | **exit 0**（eslint 那条规则根本不拦 `@/cep/fs`） |
| `npx vue-tsc --noEmit` | **exit 0**（`@/cep/fs` 是真实模块、`readTextOutcome` 是真实导出，TS 没有理由报错） |
| `node scripts/page-boundary.mjs` | **能报出这一行**，但它当前 exit 1（红的是别人家 `@/cep/readonly` 未登记），且**不在 `npm run check` 的 5 步里** |

**⇒ 「页面直读 = 0」目前只是现状事实（`grep` 数出来的），不是结构保证。** 谁下次在页面 import 一个读出口，`check` / `typecheck` / `build` **全绿**。

**关键结论（答"删白名单那一档得到什么"）**：删 `READONLY_EXPORTS['@/cep/fs']` 只把"脚本会红"从 0 变成 1 处命中，**得不到"编译会红"**——TS 的模块解析不按层拦截（`tsconfig.json:20` 的 `@/*` → `src/*` 全局可见）。**"页面层边界"这件事当前 tsconfig 表达不了**；要拿"构建红"只有两条路：①把 `page-boundary.mjs` 接进 `npm run check`（`deploy` = `check` → `typecheck` → `build`，check 红即断链）；②按 AGENTS.md §17 退到「文件顶部写清怎么用 + 留一条可执行的兜底判据」并接进 check。**没有第三条能拿到 vue-tsc 红。**
