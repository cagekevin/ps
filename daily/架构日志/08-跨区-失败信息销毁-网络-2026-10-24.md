## 二、溯源（症状 vs 病根）

三条死亡路径（按严重度）：

1. **结构不符被读成"云端没有数据"→ 覆盖云端**。`normalizeCloudPayload` 对"`units` 不是对象"一律 `return null`（`src/domain/cloud.ts:221-223`），单个坏 unit 被静默丢弃（`:226-229`）；`pullSnapshot` 原样返回这个 `null`（`transport.ts:107-110`）。引擎把 `null` 当"云端为空"：`upload` 传 `cloudExists:false`（`engine.ts:176-182`）→ 判成首次上传；`pushUnits` 用 `cloud?.units ?? {}`（`:392`）→ 全部 unit 视为 changed、无基线无冲突 → 用本地 rev=1 快照写上去。**失败伪装成"云端是空的"**，云端那份被覆盖，且没有任何痕迹。反证：`tests/cep/cloud-transport.test.ts:87-99` 断言 `{"ok":true}` → `pullSnapshot()` **resolves null**（不是 reject），即"读不懂"与"没有"同值已固化成契约。
2. **后台失败的结果无接收者，且有一条抛错路径完全无痕**。见 §一末段。最硬的一处：`refreshBaseline()` 里的 `deps.ledger.write(...)`（`engine.ts:412`）**没包 try**，而同一调用在推送路径上包了（`:492-502`）；它在 `changed.length === 0` 分支被调用（`:421-422`），写盘失败即抛出 → 冒到 `execute()` 的 `catch`（`change-sync.ts:143-146`）→ `onError` 未接线 → **既不 log 也不落 pending**，只有 `attempts++`。用户看到：上次同步时间不动，其余全绿。
3. **离线与"无事可做"同形，且空脏时不再重试**。`gate()` 在 `navigator.onLine === false` 时返回 `skip`（`setup.ts:62-64`）；队列对 `skip` 只置 `skipped=true`、不记痕迹（`change-sync.ts:135-137`）；`finally` 只在 `dirty.size > 0 || retryAt > now` 时排下一轮（`:153-154`）——启动/变可见 sweep 时脏集为空、又没进退避，**这一轮跳过之后不再重试**。UI 四条 `notice` 只覆盖 未配置/坏台账/无台账/自动同步关（`cloud-status.ts:71-84`），**没有离线分支**；此时页面显示「待推送 无」「没同步成功（空）」，与"全部已同步"逐字相同。

**上一轮那句「tick 失败不判返回值、不留痕」今天还成立吗？** 结构上成立，位置已搬家：`src/cloud/auto-sync.ts` 今天没有 tick（60 行，只有 30s 启动补偿 `:38-43` 与 `visibilitychange` `:23-27`，且 `requestSync('boot')` 是 `void`、返回值无处可判）；"不判、不留痕"实际发生在 **`setup.ts` 未接线** + 队列把 outcome 空转。措辞需改为：「队列的 outcome 无接收者；engine 内只有 4 类失败会落 pending，未落 pending 的失败零痕迹」。

**`getStatus()` 四个数字谁是"猜的"**：`syncedAt`/`rev` 是台账真值（只在真推/真拉成功后更新，`engine.ts:212-217,298-304`）；`pending` 是落盘痕迹（**截断 32 条 + 五桶原因 + 按 unit 合并**，`pending.ts:36-39`）；`conflicts` 是 pending 的投影；**`queuedUnits` 是内存脏集（`stores/cloud.ts:16`），进程重启即归零、成功即清空——它最"乐观"**。没联网时四个数字全部显示为"没有失败"：`queuedUnits=0`（sweep 不进脏集）、`pending` 未被写（闸门不记痕）。

**`pending` 落盘写失败有人知道吗？** 有人知道：`setPref` → `persist` → `notifyError`（`data/settings.ts:32,60-70`）→ `log.error` + `onSettingsWriteError` → `main.ts:63` toast「偏好保存失败」。**但** `recordPendingChanges` 不检查写入结果，`read()` 在值非数组时 `return []`（`pending.ts:16-17`）——"痕迹文件损坏"与"从没失败过"同值（见 TD-11-10）。

## 三、定海（不变式）

- 引擎的**写**（push / 台账 / pending）都做到了"失败必抛或必留痕"，唯一破坏点是把"读不懂云端"归一到 `null`（TD-11-4）。
- 缺口不在 engine 内部，而在**它的调用者**：`setup.ts` 是唯一装配点，却没把 outcome/error 两个出口接出去（TD-11-5）。

## 四、切割（收敛口）

- 收敛口一：`SyncOutcome`（`change-sync.ts:14-25`）已是现成的判别位（`ok/cancelled/errorCode/skip`），接 `onOutcome` 一个钩子即可让所有"未落 pending 的失败"至少进 `log.warn`。
- 收敛口二：`LedgerRead` 的三态（`cloud/types.ts:38-41`）是本区**做对的样板**——"读不到 ≠ 没有"；同一判据该上移到"云端快照读取"（现在只有两态 null/有）。

### 5.2 判为非债（各一句）

- `transport.ts:19,56-57,94-96` 20s 超时 → `CloudError('同步超时')`：失败有码、有语义，不把超时当成功——**合法转译**（CEP 无 `AbortController` 时无超时属 `UNVERIFIED`：Chromium 99 假定有，未真机确认）。
- `transport.ts:31-40` 单进程 FIFO：把"撞车"从假网络错误改成排队，是**合法改进**（T-77）。
- `download` 部分写回失败（`engine.ts:287-296`）：`partial.failed` + 专属 `CLOUD_WRITE_FAILED` + 不写台账 + 命令层抛原文——"提交了"与"没提交"可区分，**合法转译**。
- `pushUnits` 单 unit 读失败（`engine.ts:360-375`）：`pending('collect-failed')` + 保留 `pending:failedIds` + 文案「本地这项数据读不出来，没上传」——**合法转译**。
- 偏好写失败（`data/settings.ts:32` → `main.ts:63`）：log + toast 双信号，**合法**。
- `getStatus` 坏台账 `syncedText='读不到'`（`cloud-status.ts:88`）：挡住"尚未同步"的误导，**合法**。
- `hasCloudLedger()` 只认 `ok`（`ledger.ts:89-91`）：护栏语义的一部分，**合法缺省**。
- `refreshBaseline` 不新建台账（`engine.ts:405-419`）：防"内容恰好相同"顺手解除新设备护栏，**合法缺省**。
- `set/index.vue:197` `cloud.refresh()` 未 catch：由 `installErrorHandlers` 的 `unhandledrejection` 接住（`utils/error-handler.ts:44-46`）→ log + toast，**合法**。
- adapter 层（`entries/font-tags.ts:12-14,19-27` 为代表）：读错抛、写错回 `{ok:false,message}`，交由 engine 转译，**合法**。
