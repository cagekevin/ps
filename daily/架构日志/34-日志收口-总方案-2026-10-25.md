**`log.clear()` 的来历（git log 取证，回答"谁留下的、为什么写"）**：

- **`80063e4`（首版 logger.ts，cagekevin）**：`clear()` 只清 `buffer`（`buffer.length = 0`），是**内存环形缓冲**（最早 200 条）时代的产物 —— 那时没有落盘、没有 `history`，"清空"只有"清现场缓冲"一个语义，测试里调它是合理的隔离手段（两个用例之间清干净）。
- **`6443130`（2026-10-24，logger 日志落盘）**：新增 `history`（上一会话读回的落盘行）+ `__resetLoggerForTest()`（明确注释「仅测试用：卸掉落盘口并清历史，模拟面板重开前把状态清干净」），但**没有同步收窄 `clear()`** —— `clear()` 仍然 `buffer.length = 0; history.length = 0`，从"清现场"悄悄变成"清现场 + 清上一会话证据"。**这是半态**（加了 `history` 却没改 `clear()` 的职责边界，违反 6.3 清剿尾巴）。
- **`e9d5daa`（2026-10-24，TD-11-7 离线跳过留痕）**：`tests/cloud/offline-skip.test.ts` 引入 `log.clear()`（全仓**唯一**一处调用），用它做用例间隔离 —— 但那时 `clear()` 已经会连 `history` 一起抹（虽然这个测试没接落盘 sink，`history` 本来就是空的，所以实际没出事）。

**结论：`log.clear()` 不是"谁故意留下的破坏性 API"，是 80063e4 的"清现场缓冲"语义，在 6443130 加了 `history` 后没被同步收窄的残留** —— 责任是 6443130 那次"只加不清"的半态，不是首版作者的错。真正的测试隔离入口是 `__resetLoggerForTest()`（有注释、只给测试用、语义完整），`log.clear()` 是它的残缺前身。**处置（L2）**：把 `tests/cloud/offline-skip.test.ts:116` 改调 `__resetLoggerForTest()`（语义更对：清 sink + 清 history + 清 buffer），然后删 `log.clear()`（真死删，`__resetLoggerForTest` 已覆盖它全部能力）。

## 1. 现状（2026-10-25 当场实测，每条都跑了命令）

### 1.1 日志是什么（口径）

**日志** = 为开发者/排查者记录「刚才发生了什么」的结构化输出，供**开发者**（不是用户）事后查看。
回答的问题是「**开发时发生了什么**」，不是「用户看到什么」（后者是用户文案/提示语，已由上一条横切收口）。

三层结构（`src/utils/logger.ts` 注释）：

1. **内存缓冲**（最近 200 条）：`log.dump()` + `__pszDump()` 的现场；
2. **落盘**（`LogSink` → `cep/log-file.ts`）：关掉重开还查得到；
3. **控制台**：开发时看的东西（`console.warn`/`console.error`）。

### 1.2 什么算日志 / 什么不算（口径边界，**唯一一处**）

| 算日志（本横切收口对象）                                                                                                                                                               | 不算日志（不归本横切）                                                                      |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `log.debug/info/warn/error(scope, msg, detail)` 的**记录动作**                                                                                                                         | **用户文案**（`feedback.*`、`msg.*`、toast 提示）—— 已由上一条横切「用户文案」收口          |
| `log.dump()` 的**读取动作**                                                                                                                                                            | **错误分类**（`CepError`、`describeCepError`、`codeText`）—— 错误是业务语义，日志只是记录它 |

- **`window.__pszDump` 不是第二个读取入口，是 `log.dump()` 的全局导出面**：`logger.ts:153` 是 `window.__pszDump = () => log.dump()` —— **一行委托**，同一个 `log.dump()` 逻辑，只是挂到 `window` 上（`src/env.d.ts:65` 的 `Window.__pszDump` 声明）。**谁在用**：内部代码**不**调它（`DebugLog.vue:17` 直接 `log.dump()`，当场 grep `window.__pszDump` 在 `src/cep/` `tests/` `index.html` = 0 命中）；它面向的是**外部**——CEP 的 DevTools 里手敲（`logger.ts:152` 注释），或宿主脚本 `window.__pszDump()` 取现场。所以它是**同一个能力（读日志现场）的两条路：一条给内部（`log.dump()` import）、一条给外部（`window.__pszDump` 全局桥）**，不是两份实现。**不构成"第二套实现"**（一归判据①要求"N 份实现收 1 份"，导出面是 0 份新实现）。
- **`log.clear()` 是幽灵 API**：它不是别名，是**真的第二套清空逻辑**（同时抹掉 `buffer` + `history` 上一会话证据），0 处生产消费（仅测试调），且做了"清现场 + 清历史"两件事（不该一个函数干两件）。与债 16 命中。
- **判定一句话**：`__pszDump` = **同一能力的外部导出面**（`log.dump()` 的全局桥，给 DevTools/宿主脚本用，无第二份逻辑）；`log.clear()` = **幽灵破坏性 API**（独立逻辑 + 无消费者 + 毁证据）。两者表面都是"0 生产消费"，但前者是导出面不是重复实现、后者是重复且危险，故 L2 只收 `log.clear()`（+ Icon.vue 裸 console），`__pszDump` 保持不动（它符合"唯一入口在 `logger.ts`"的落点，只是对外多一个全局桥）。⚠️ **真机行为 UNVERIFIED**：CEP/PS 宿主脚本实际能否在面板外调到 `window.__pszDump`（跨 frame/进程可见性）没在真机验过，只验了代码路径存在。

**fs.ts:499/504 调用点核对（当场查，回答"调用方分得清吗"）**：

`psScriptsDir()` 全仓**只有一个真实调用方**：`src/commands/system.ts:50`（`system.copyToScripts` 命令）：

```ts
const dir = await psScriptsDir()
// 解析不出路径必须报错：静默跳过会让用户以为拷成功了
if (!dir) {
  throw new CepError('IO', msg.command.text.copyFileDirNotFound)
  // → 用户看到："拷贝文件错误：找不到 PS 的脚本目录，请手动复制或者开启管理员权限"
}
```

**结论（订正，不再说"没人看得见"）**：

- **用户侧可见**：`null` → 抛 `CepError` → `useCommand` 统一 toast，用户看到明确的失败提示（"找不到 PS 的脚本目录，请手动复制或者开启管理员权限"）。**不是静默吞掉**。
- **开发者侧：有日志，但同样只有笼统原因**（当场核）：`registry.ts:149` 的 `log.warn('cmd', '${id} 失败：${reason}', e)` 会记这条失败（`execute` 的 catch 归一必经此），**日志里确实有一条**。但 `system.ts:52` 抛的是 `new CepError('IO', msg.command.text.copyFileDirNotFound)` —— **原样固定文案，不带 `psScriptsDir` 内部任何上下文**（是脚本业务错？超时？`hasCep()` false？全没记）。所以开发者查日志只能看到"system.copyToScripts 失败：拷贝文件错误：找不到 PS 的脚本目录"，**分不清**「脚本目录没权限」和「脚本返回了业务错」——**可见，但不可区分**。
- **但调用方分不清"脚本没跑起来"和"脚本报了业务错"**：`null` 同时覆盖三种情况——(a) 脚本业务错误（jsx 内 `catch(e){return ERR_PREFIX+...}`，:492-494 拼的脚本自己会返回错误串，:498 `raw.startsWith(ERR_PREFIX) → return null`）、(b) `evalScriptRaw` 真超时/宿主异常（catch 分支，:504）、(c) `hasCep()` 为 false（:492 直接 return null）。三者对调用方完全无差别。
- **但这个"分不清"在当前唯一调用点上无害**：`system.ts` 的处理是"拿不到路径就报错并建议手动复制"，对 (a)(b)(c) 三种情况**都该走同一条路**（都是"路径没拿到，得让用户自己来"），不需要区分是脚本错还是超时。**所以功能上没有走偏**，只是**诊断信息丢失**（开发者事后无法从日志/错误文案判断到底是哪一类，全靠一句笼统的"找不到脚本目录"）。
- **对比 `readTextViaJsxOutcome`（fs.ts:467-482，同一文件，写法更讲究）**：它对同样三种情况**分开表达**（`{status:'ok'}` / `{status:'notSeen'}`（`JSX_MISSING_PREFIX`） / `{status:'error', reason}`），catch 里也带 `reason`。`psScriptsDir` 没有沿用这个形态，是**同文件内两套错误表达**，属"一归"可改进点（非紧急）。

**定性（订正 2，见上"用户可见 + 开发者日志可见"两条核对）**：fs.ts:499/504 **不是"完全没人看得见"**（用户 toast 看得到，开发者日志里也有 `registry.ts:149` 那条记录），但**可见信息被两级归一**——`psScriptsDir` 内部把三种失败归一成 `null`（丢 `reason`），`system.ts:52` 又把 `null` 归一成固定文案（丢 `code`/上下文）——**开发者事后查日志能知道"失败了"，但分不清"哪种失败"**（权限？超时？脚本业务错？）。严格按 ADR-0014「读可降级但必须标记」看，缺的是 `degraded`/`reason` 标记一路传到日志；按"失败诚实可见（根部炸开）"看，错误在**根部（`psScriptsDir`）就没带原因**，一路传上去只剩笼统一句。**这是"诊断信息丢失"，不是"零痕迹"**——比 #5/#10/#12（连"失败了"都没人知道）轻，但仍不合格，挂账后续批次。

**3 处真静默的共同模式**：**失败被归一成"空值"（`''`/`null`）且与"本来就是空"合并**，正是 ADR-0014「失败归一空值」形态——**归 S1（静默失败收口）独立批次**（改判别联合 `{value, degraded}` 或补可见信号，不是补 log），**不在本横切 L2/L3/L4 范围**（L2 只收 console 漏口 + `log.clear()`）；归属定死见 §2「§1.4 挖出来的额外发现，归属定死」表，不留"已登记没人做"。

**判定一句话（订正）**：**"所有 catch 都打日志"不是判据**（会制造重复日志和刷屏）；**判据是"每个 catch 的失败都有可见去向"**（log / rethrow 给上层记 / 设可见信号 / 计数或判别联合传出，四选一），103 个 catch 中 **100 个满足**（失败有可见去向），**3 个真静默**（#5/10/12，用户和开发者都看不见）+ **2 个精度丢失**（#14/15，用户看得见但开发者分不清原因，归 S1 独立批次，不在 L2/L3/L4）。

**判据①的范围（唯一一处，不复述）**：判据① = `src/` 里除 `logger.ts` 外 `console.*` = 0，**只管 `src/`（面板运行时代码）**。`tests/`（0 处）、`index.html`（0 处）、`scripts/`（533 处）**都不在本横切范围**，依据是**横切本身的定义，不是"eslint 放行"**：

- **本横切的名字是「面板运行时的日志出口」**（§1.1 口径：为开发者记录「刚才发生了什么」供事后排查）—— 它管的是**在 CEP/PS 里跑的面板**怎么留痕迹。`scripts/**` 是**构建期/工具期的 Node 进程**，不在面板里跑，天然不属于这条横切（跨进程 = 跨横切，普查判据①「同一层可以多份，跨层不行」）。
- **`tests/` / `index.html`：不是漏**，因为它们本来就没有 `console.*`（0 处），无对象可收。

2. **补它不越权**：§17 的表头写「**这张表是唯一清单**，不要在别处再列一份」——**清单的完整性本身是这张表的职责**。发现清单缺一行而不管，就是让"唯一清单"名不副实（`一归`）。**登记不是收口，是收口的必要配套**。

   - 错误码（定义）→ `utils/errors.ts`（`CepErrorCode`）· 谁能用：全仓抛错处 · 判据：新增码只在此处加

普查第 7 项「失败表达」的**具体范围**（`daily/架构日志/30-横切普查-14类-2026-10-25.md:20`）是**错误码/枚举/文案表散落、裸 string 不用类型枚举**——`commands/cloud.ts:17` COMMAND_CODE、`pages/set/cloud-status.ts:50` CODE_TEXT、`cep/cloud/setup.ts:87` retryPolicy、`cep/cloud/pending.ts:37` CODE_HINT，`CloudErrorCode` 9 码实际流动 11 码，`errorCode?: string` 裸 string 没人用枚举做类型。**这是"码表第二份真相"问题**（同一错误码的文案/分类散在多张表）。
