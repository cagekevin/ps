## 六、踩到的坑

1. **`resolve --note` 有字符黑名单**（竖线 / `]` / `{` / `}`），证据里有就要重写句子。
   第一次交的几个 note 里带 `:118 return raw as unknown as T` 之类，直接被写入口拒了。
   ⇒ **写 note 时就避开这些字符**，别指望它能含代码片段。
2. **用例名里有全角括号也会被拒**：TD-13-9 那条用例原文是
   `失败路径不产出「没选中」形状的快照（旧实现会返回 {false, 0}）`，里面有一个 `{`，
   整段不能进 claim ⇒ claim 只能截到 `失败路径不产出「没选中」形状的快照`。
3. **claim 必须 逐字出现 在输出里**：凭记忆写用例名会被拒（TD-12-24 第一版少了中间半句，重写后才通过）。
   ⇒ 流程改成：**先 `grep -n "it("` 拿原句 → 拷进 claim → 再跑 `resolve`**。
4. **note 写歪可以用再一次 `resolve` 覆盖**：我先填错过 TD-13-1 / TD-13-3 / TD-13-5 / TD-12-23 / TD-12-24 / TD-12-26 / TD-12-28 / TD-12-10 几条，
   全部**重跑 `resolve` 覆盖**，
   重跑时**不带 `--drop-original`**，所以 `原记「…」` 逐字保留、只换 badge 与 solution 段。
5. **别用整包 `npm test` 的 `N passed` 当 claim**（整包计数会随任何一处新增用例漂）。本轮 22 条全部是单文件 `vitest run <file> --reporter=verbose` + 用例名，粒度足够小，别人加用例也不会漂。
6. **能断「用例名」就别断数字**：本轮唯一一条断数的是 TD-12-10，而它数的是**守卫输出里那一行带文件行号的句子**（不是裸数字），其余 21 条全断用例名。
