### 表 C · 判别语法清单（最容易漏的一张）

> **本表要数的不是"用了哪几种语法"，是"收窄这件事有几种判别语法"** —— 判据：> 1 种 ⇒ 一定还有形状没收。

```bash
# ① 断言族（"盖章式"收窄：不证明，直接断言）
git grep -nP "\bas\s+(?!any\b|const\b|unknown\s+as\b)[A-Za-z_{(]" -- src | wc -l   # 164
git grep -nP "\bas\s+unknown\s+as\b" -- src | wc -l   # 2（都是注释）
git grep -nP "\bas\s+any\b" -- src | wc -l            # 0
git grep -nP "[A-Za-z0-9_\)\]]\![.\)\],;\[]" -- src | grep -v "!==" | wc -l   # 0（非空断言）
git grep -nP "\bsatisfies\b" -- src | wc -l           # 0
git grep -nP "=\s*<[A-Z][A-Za-z0-9_]*>" -- src | wc -l   # 0（尖括号断言）

# ② 证明族（"检查式"收窄：真判，返回布尔）
git grep -nP "\)\s*:\s*\w+\s+is\s+[\w<{]" -- src | wc -l   # 26（类型谓词声明）
git grep -nP "\binstanceof\b" -- src | wc -l                # 48
git grep -nP "typeof .*(===|!==) '" -- src | wc -l          # 224
git grep -nP "'[a-zA-Z_]+' in |\"[a-zA-Z_]+\" in " -- src | wc -l   # 10
git grep -nP "Array\.isArray\(" -- src | wc -l              # 97
git grep -nP "[!=]== (null|undefined)" -- src | wc -l       # 92
```

**「种数」分两层，必须分开数**（`wc -l` 数的是**行**，测不到"种"）：

**① 判别「语法形态」种数**（目标 = 收到 1 个）：
```bash
{ git grep -hoP "\bas\s+(?!any\b|const\b)[A-Za-z_{(]" -- src
  git grep -hoP "\)\s*:\s*\w+\s+is\s+[\w<{]" -- src
  git grep -hoP "\binstanceof\b" -- src
  git grep -hoP "typeof .*(===|!==) '" -- src
  git grep -hoP "'[a-zA-Z_]+' in " -- src
  git grep -hoP "Array\.isArray\(" -- src
  git grep -hoP "[!=]== (null|undefined)" -- src
} | sed -E 's/.*\b(as|is|instanceof|typeof|in|isArray|==|!=)\b.*/\1/' | sort -u | wc -l
```
实测 = **13 种**（把 0 命中但语法存在的 `as unknown as` / `as any` / `!` / `satisfies` / `<T>x` 也算进去 ⇒ **17 种**）。

**② 判别「字段/位」种数**（目标 = 收到 1 个）：类型收窄**不产出判别字段**（这是它和 39 号文「解析」的本质差别）——
它的判别位是**布尔返回值**，所以"种数"落在**语法**上，不落在字段名上。
唯一例外是表 A 第 2 行的 `Decoded|DecodeFail`（`fail` 位）—— 那是**解析**的形状，不是收窄的形状。

**③ 行数 vs 种数对账**（同一时点两个数并列，只有行数降 = 假收口）：
```bash
git grep -nP "\bas\s+(?!any\b|const\b|unknown\s+as\b)[A-Za-z_{(]" -- src | wc -l   # 164（行数）
git grep -nP "\bas\s+(?!any\b|const\b|unknown\s+as\b)[A-Za-z_{(]" -- src | grep -oP "\bas\s+\K[A-Za-z_{(][A-Za-z0-9_$.<>,\[\]{} ]*" | sort -u | wc -l   # 目标类型种数
```

**判据判定：收窄语法 = 13 种形态（17 种含零命中） ≫ 1 ⇒ 一定还有形状没收。**

**但这里要做一个本轮自己推导的修正（38/39 号文没做过的）**：
**"收窄语法收敛到 1 种"这个目标本身是不成立的、也是错的。** 因为：
- `typeof x === 'string'`、`instanceof Error`、`in`、`Array.isArray` 是 **TS 语言内建的、不可替换的**收窄手段；
  **一个类型谓词的实现体内必须用它们** —— `guards.ts:10` 自己就是 `!!value && typeof value === 'object' && !Array.isArray(value)`。
  ⇒ 收窄语法的收敛目标**不是"语法只剩一种"**，而是"**出口只剩两个**"（见 §4 判据 2）。
- 把 `typeof`/`instanceof` 内联收编成"底座函数"是**错的收口方向**（38 号文已在「形状判定」上撞过：`isRecord` 的实现体也用 `typeof`）。

## 3. 一个本轮自己推导的分类：**收窄有两族，底座只收编了一族**

## 4. 六条判据（「类型收窄」收口 = 六条同时成立）

> 每条一条命令能复算；**判据 2 / 4 是"区分真收口和看起来收口"的两条**；**判据 6 是本轮探针实证的一条**。

**判据 1 · 断言清零（`as` 只许出现在第三方边界，且带理由）**
宽 → 窄的转换只许两种走法：**证明**（谓词/`decode`）或**第三方边界断言**（带 `// 断言理由：`）。
```bash
git grep -nP "\bas\s+(?!any\b|const\b|unknown\s+as\b)[A-Za-z_{(]" -- src | wc -l   # 现 164（含 as const 44 + 注释 15 + import 别名 3）
# 去掉 as const / 注释行 / import 别名后的真·收窄断言：
git grep -nP "\bas\s+(?!any\b|const\b|unknown\s+as\b)[A-Za-z_{(]" -- src \
  | grep -vE ":[0-9]+: *(\*|//)" | grep -vE ":[0-9]+: *(import|export [^=]*from)" | wc -l   # 现 146
git grep -nP "\bas\s+Record<string, unknown>" -- src | grep -vE ":[0-9]+: *(\*|//)" | wc -l   # 现 45（21 个文件；含注释 49）
```
**收口 = 断言数降到"第三方边界且带理由"那几条**；146 只许降不许升。
**注意 `as const` 44 处不是收窄**（是字面量类型固定），**不计入**。

> **⚠️ 第四遍修正（见 §A / §F）**：① 146 处里**只有 135 处是"零证明断言"**，
> 另 11 处是**合法/中性**（字面量收窄 6 · `undefined as number | undefined` 1 · `as readonly`/`as Partial` 4）
> ⇒ **判据 1 的验收口径应改成「零证明断言 135 处归零」，不是「`as` 归零」**（否则会误伤 11 处合法断言）。
> ② `as` **不是无条件的盖章**：TS 有 TS2352 重叠检查，只是在**源为 `unknown`**（本仓最常见起点）
> 或**源/目标带索引签名**（5 个接口）时失效 ⇒ **"零证明"是那两种情形的性质，不是 `as` 的普遍性质**。

**判据 2 · 出口只有两个（证明只有一个入口，带原因的只有一个契约）**
「把宽类型收成可信类型」只许从两个出口出去：
**出口 1 = 布尔证明**（`guards.ts` 的谓词，失败 = `false`）· **出口 2 = 带原因的证明**（`decode.ts` 的 `Decoded|DecodeFail`）。
**`as` 断言不是出口 —— 它是第三个出口（零证明的出口），必须归零。**
```bash
# 出口 1 的调用点
git grep -nP "\b(isRecord|isUnknownArray|isString|isArrayOf)\(" -- src | wc -l   # 现 75（24 文件）
# 出口 2 的实现数
git grep -nE "Decoded<.*> \| DecodeFail" -- src | wc -l   # 现 23（39 号文口径）
# 第三个出口（必须归零）
git grep -nP "\bas\s+(?!any\b|const\b|unknown\s+as\b)[A-Za-z_{(]" -- src \
  | grep -vE ":[0-9]+: *(\*|//)" | grep -vE ":[0-9]+: *(import|export [^=]*from)" | wc -l   # 现 146
```
**"看起来收口"的判据**：把 `as` 改个写法（`as T` → `as unknown as T` → `as any`）而数量不变 ⇒ 假收口。

**判据 3 · 谓词名 = 所证（`x is T` 必须在类型层排除所有不满足 T 的值）**
```bash
# 具名谓词 16 个
git grep -nP "(function|const)\s+is[A-Za-z]+\s*[=(][^\n]*\)\s*:\s*\w+\s+is\s+[\w<{]" -- src \
  | grep -vE ":[0-9]+: *(\*|//)" | wc -l   # 现 16
# 其中"实现只写 isRecord(x)"的假证明 4 个
git grep -nP "(=> isRecord\(x\)|return isRecord\(value\)|return isRecord\(x\))$" -- src | wc -l   # 现 4
```
**4 处假证明**：`isRawTag`（`cep/data/index.ts:38`）· `isRawStar`（`:39`）· `isCommonUseItem`（`domain/common-use.ts:407`）· `isQuickFont`（`domain/font-set-config.ts:115`）。
**注意：这 4 处都有注释说明为什么**（`font-set-config.ts:114`「磁盘上的真实形状未经真机验证，过严会把正常文件判成坏文件」；`common-use.ts:405`「元素进 `CommonUseItem[]` 时用证明，不用 `as`」）——
**它们是"有意的不严格"，不是笔误**。所以**正确处置不是"补字段证明"（会把好文件判成坏文件）**，而是：
**要么谓词返回 `value is Record<string, unknown>`（不承诺字段），要么类型改成"字段全可选"** ——
**关键是别让类型名承诺一个实现没证的东西**。

**判据 4 · 收窄失败必须有可见信号（不许"静默丢条目"）**
`filter((x): x is T => …)` 把"收窄失败"变成"**静默丢弃**"—— 这和 39 号文解析债 7（`style-library-repo.ts:492` 丢条目）**同根**。

**收口 = 走 `decodeIndexed`/`decodeList`（`decode.ts:137/155`，坏条目整份失败 + 原因），不许 filter 掉。**

**判据 5 · 底座必须被登记（`横切能力.md` 里这一行不能还是"（待补）"）**

## 5. 按刀 1 四层的分层结论（哪些该被同一条判据管住，哪些是合理分层）

**四层判据（刀 1 原文）**：问它「失败了说不出原因」会不会伤人 —— ① 说不出原因=只报 errno（**可以**）；②③④ 说不出原因=**不行**。
**处置规则**：① 只许两个（文本/字节）；② 只许一个入口一个形状；③ 只许一个契约；④ 允许存在但必须有判别位、不许带可忽略字段。**判据：层数=形状数=入口数。**

| 层 | 职责 | 本仓形状（表 A 编号）| 归哪条判据 | 判定 |
|---|---|---|---|---|
| **① 观测层** | 把外部世界变成三态（在不在/读不读得到/值是什么类型）| **#1 `guards` 谓词族**（4 个）· **#4/#5 域内谓词**（13 个）| 判据 3（谓词名 = 所证）| ⚠️ **"值是什么类型"这一档在底座只有 A 族，B 族（DOM）0 份**；**域内 13 个谓词与底座 4 个谓词同层多份**（`guards.ts` 收编的是"通用形状"，域内那 13 个是"业务形状"——**分档合理**，但其中 4 个"只证是对象"是**假证明**，判据 3 管）|
| **② 判据层** | 把观测+解析折成结论（能不能当 T 用、坏了什么原因）| **#2 `Decoded\|DecodeFail`** · **#3 `isDecodeFail`** | 判据 2 + 4 | ✅ **合理分层**（`Decoder<T>` 类型层强制"失败说不出原因编译不过"，39 号文已确认是真结构保证）|
| **③ 纯解析层** | 把不可信形状收成可信形状 | **23 个 `decode*`** | 判据 2 | ✅ **合理分层**（`decodeIndexed`/`decodeList` 的 `isItem` 必填 = 元素级证明的唯一通道）|
| **④ 业务结论层** | 表达一个业务判断（该域特有的三态）| **#10 `filter` 内联谓词的丢弃** · **#6 `as` 断言**（伪装成业务结论）| 判据 1 + 4 | ❌ **不成立**：**#6 的 146 处断言在冒充"业务结论"**（`item as ActionItem` 假装"这就是 ActionItem"），**#10 的 6 处 filter 在冒充"结论层"**（把"不是"当成"没有"）|

**层数=形状数=入口数？—— 对不上**：
- 层 **4** 个，形状 **17** 个（表 A）⇒ **形状数是层数的 4.25 倍**；
- 入口 **7** 个（表 B）⇒ **与层数不等**；其中入口 1（`guards`）只覆盖了 **75 个调用点**，
  **146 处 `as` + 92 处内联 `Array.isArray` + 83 处内联 `typeof === 'string'` + 45 处内联 `typeof 'object'` = 门外 366 处同类判据**（约 80% 绕过底座）。

**该被同一条判据管住的 —— 它们全是"这个宽值能不能当 T 用"，只是用了不同语法**：
`guards` 4 谓词 · 域内 13 谓词 · `as T` 146 处 · 内联 `typeof` 224 行 · 内联 `Array.isArray` 92 处 · `instanceof` 48 处 · `in` 10 处 · `null/undefined` 判 92 行。
**⇒ 判据 2（出口只有两个）是本横切的收口主判据**，判据 5（语法种数）是它的**观察量**，不是目标。

**`instanceof Error` 一族（47 处）单独定性 —— 本轮自己的推导**：
`instanceof` 在 TS 里是 **`unknown` 收窄到具体类的唯一语言手段**，
`catch (e)` 拿到的 `e` 是 `unknown`，**不靠 `instanceof` 就没有任何办法知道它是 Error**。
⇒ **"把 47 处 `instanceof` 收编成 1 处"这个目标是错的**（会把 `instanceof` 塞进一个函数，反而丢掉收窄能力）。
**但有一处是真重复**：`x instanceof Error ? x.message : String(x)` 这个**模式**散写 **33 处**，
而底座 `utils/error-text.ts:12` 的 `describeCepError` 已经做了同样的事（只是它多管了一层 `CepError` 的码→文案）。
⇒ **该收编的不是 `instanceof`，是"把 unknown 错误变成一句 message"这个动作** ——
**底座缺一个 `messageOf(e: unknown): string` 原语**（`describeCepError` 是它的超集，但语义是"翻成人话+码文案"，不是"取 message"）。
**这是"底座该有却没有"的第二例**（第一例是 B 族 DOM 收窄）。

## A. 盲区 26/27 · **推翻了前三遍的核心论断**：`as` 不是"零证明"，是"**重叠逃逸**"

### A1 · 前三遍说错了一句（必须更正）

前三遍（§0 / §2 表 A #6 / §4 判据 1）反复写：

> 「`as` 断言 —— **无判别位 / 不表达 / 零证明**」

**这句话是错的。** 本遍用**三个探针**（每个都自动还原）把 TS 的真实规则测出来了：

```bash
# 探针 1：unknown as T —— 类型系统放行吗？
cat > src/__probe_ov.ts <<'EOF'
export function a(x: unknown) { return x as { id: string } }
export function b(e: PointerEvent) { return e as { id: string } }
export function c(g: { text?: string; name?: string }) { return g as { id: string } }
EOF
npx vue-tsc --noEmit 2>&1 | grep -E "__probe_ov|error TS"
rm -f src/__probe_ov.ts
```
**实测输出（只有 1 行）**：
```
src/__probe_ov.ts(2,45): error TS2352: Conversion of type 'PointerEvent' to type '{ id: string; }'
  may be a mistake because neither type sufficiently overlaps with the other.
```
**⇒ 三行里只有第 2 行报错**：
| 探针 | 表达式 | TS 判 | 读法 |
|---|---|---|---|
| 第 1 行 | `unknown as {id:string}` | **✅ 通过** | `unknown` 与**一切**类型重叠 ⇒ 断言永远合法 ⇒ **零证明** |
| 第 2 行 | `PointerEvent as {id:string}` | ❌ **TS2352** | 两个具体类型**无重叠** ⇒ TS 拦下 ⇒ **不是零证明** |
| 第 3 行 | `{text?:string; name?:string} as {id:string}` | **✅ 通过** | 源有 `[key:string]:unknown` 索引签名 ⇒ 与**一切**目标重叠 ⇒ **零证明** |

**⇒ 修正后的论断**：
**`as` 不是"无条件的盖章"，TS 对它有**重叠检查**（TS2352）；但这条检查在两种情况下完全失效：**
1. **源是 `unknown`**（本仓最常见的起点：JSON.parse、事件、宿主返回）；
2. **源或目标带索引签名**（`[key: string]: unknown`）。

**⇒ 这才是 `as` 在本仓失控的真正机制 —— 不是"TS 管不了 `as`"，是"TS 管得了，但 `unknown` 和索引签名让 146 处断言全部落在它的盲区里"。**

**这个修正改变了修法**：原判"禁掉 `as`"太粗；真解是
**① 把源从 `unknown` 变成具体类型（`let x: unknown` 之后先证再断），
② 把目标从带索引签名的宽接口变成窄接口（去掉 `[key: string]: unknown`）** ——
**这两条都是"改生产者"，正是硬规则 20 规矩二与 ADR-0024 已经在说的话。**

## I. 一句话总结（第四遍）

第四遍**推翻了自己前三遍的一个核心论断**：

## C. 盲区 36 · `as` 的**失效条件**（第四遍只答了一半）

第四遍答了"源是 `unknown` / 带索引签名时检查失效"。**这一遍把"哪些形态是安全的"测出来**：

| 探针 | 结果 | 读法 |
|---|---|---|
| `unknown as {id:string}` | ✅ 通过 | **源是 `unknown`** ⇒ 零证明 |
| `PointerEvent as {id:string}` | ❌ TS2352 | 两个具体类型无重叠 ⇒ **TS 拦得住** |
| `{text?:string;name?:string} as {id:string}` | ✅ 通过 | **源带索引签名** ⇒ 零证明 |
| `x as {id:string}[]` 后访问 `a[0].missing` | ❌ **TS2339 报错** | **断言到数组后，元素类型仍被检查** ⇒ 比断言到对象**更严** |
| `(r.id as string)`（`r` 是 `Record<string,unknown>`）| ✅ 通过 | **二次断言会"洗白"** —— 第一次断言报的 `TS18046 'r.id' is of type 'unknown'` 被第二次断言消掉 |
| `typeof x === 'string'` 后 `x.length` | ✅ 通过 | **TS 的收窄是真实有效的** |
| 收窄后 `x.foo = 1`（`x` 是 `object`）| ❌ **TS2339 报错** | 收窄**不会**因为赋值而失效 |
| 闭包 / `setTimeout` 回调里用收窄后的 `x.length` | ✅ 通过 | **收窄跨闭包不失效**（TS 5.x 的 const 窄化）|

**⇒ 第五遍补上的判据（第四遍没有的）**：
**`as` 的安全度不取决于"是不是 `as`"，取决于「源类型」**：
- 源是**具体类型**（`PointerEvent`）⇒ **TS 会用重叠检查拦** ⇒ 相对安全；
- 源是 **`unknown`** ⇒ **零证明**；
- 源/目标**带索引签名** ⇒ **零证明**；
- **目标是非索引签名的数组** ⇒ **元素类型仍被检查** ⇒ 比对象更严。

**⇒ 二次断言是"洗白器"**：`as` 消掉一个错误，下游就再也看不见那个错误了。
仓里现在 **2 处**二次断言（`commands/font.ts:109` `record.tags as RawTag[]`·`record.stars as RawStar[]` 同句两个；
`pages/commonUse/useCommonUseOptions.ts:46` `(… ?? fallback) as T) as Ref<T>`）——
**`useCommonUseOptions.ts:46` 那处正是 §6 债 3 的越权点**（兜默认 + 断言 + 再断言）。

## C. 盲区 42/43 · **`.d.ts` 声明与运行时现实矛盾**（第六遍最重的一条）

### C1 · 两处注释对同一个事实给了**相反**的断言

| 位置 | 原文 |
|---|---|
| **`types/cep-node.d.ts:11`** | 「只声明我方真正用到的两个字段：`env`（`fs.ts` 的 `userDir`）、`pid`（`fs.ts` 的 `uniqueTmpPath`，D-42）。**写成必填是*故意的***：**两处调用点都先过 `nodeRequire` / `hasNode()`，Node 不在就到不了那里**。」 |
| **`src/cep/paths.ts:26`** | 「`process` 由 CEP 的 --enable-nodejs 注入（形状在 `types/cep-node.d.ts`）；**无 Node 时它不存在**，`?? {}` 保留：下一行 `nodeRequire('path')` 会抛 NO_NODE。」 |

**⇒ 「两处调用点都先过 `hasNode()`」这句话是假的**：
`types/cep-node.d.ts` 自己说 **`env` 的调用点是 `fs.ts` 的 `userDir`**，
而 **`userDir()` 的第 1 行就是 `globalThis.process?.env`** —— **它自己就是那个"调用点"，且它没有 `hasNode()` 守卫**。

```bash
git grep -n "userDir()" -- src | grep -c "hasNode"    # → 0
git grep -c "userDir()" -- src | awk -F: '{s+=$2} END {print s+0}'   # → 60 处调用点，0 处带守卫
```

### C2 · 但**当前不会崩**（阴性发现，如实记）—— 两条独立的保护

| 保护 | 机制 |
|---|---|
| **① `?.` 兜住了** | `globalThis.process?.env` —— 无 Node 时 `process` 是 `undefined` ⇒ `?.` 返回 `undefined` ⇒ `?? {}` ⇒ **不崩** |
| **② `nodeRequire` 抛在前** | `userDir()` 第 2 行 `nodeRequire('path')` 在无 Node 时抛 `CepError('NO_NODE')` ⇒ 后面 3 行不执行 |

**`uniqueTmpPath` 那处更安全**：`disk-write.ts:42` 的 `globalThis.process.pid`（**没有 `?.`**）——
但它在 `atomicReplace` 里，而 `atomicReplace` 的**第 1 行**就是 `const fs = nodeRequire('fs')` ⇒ **无 Node 时 `nodeRequire` 先抛** ⇒ `process.pid` 轮不到。
**⇒ `disk-write.ts:42` 看着危险（无 `?.`），实际安全 —— 但它的安全性依赖"调用顺序"这个**没有任何门禁保证**的事实。**

### C3 · **真正的缺口在类型层**

```bash
# 探针：declare var process 必填时，?. 与 globalThis 访问会不会被 TS 拦
cat > src/__probe_proc2.ts <<'EOF'
export function f() { const p = globalThis.process; return p.pid }
export function g() { return globalThis.process?.env.APPDATA }
EOF
npx vue-tsc --noEmit 2>&1 | grep -E "__probe_proc2|error TS"
rm -f src/__probe_proc2.ts
# → 实测：exit 0，0 报错
```
**⇒ 因为 `declare var process` 声明成**必填**，TS 眼里 `process` 一定存在**：
- `globalThis.process.pid` **0 报错**（哪怕运行时可能整个 `process` 都不存在）；
- `globalThis.process?.env` 的 `?.` **TS 不报错，但也不提示"多余"** ⇒
  **"无 Node 时它不存在"这个真实风险，在类型层完全不可见。**

**⇒ 这是硬规则 20(a) 这条路线自身的盲区**：
**「先让类型存在」解决的是"类型缺失"，但它默认了"声明 = 现实"。**
**当第三方对象是"可能存在"时（CEP 的 `--enable-nodejs` 是开关），必填声明就是把风险藏进了类型层。**
**⇒ 正确声明应是 `declare var process: CepNodeProcess | undefined`** ——
**那样 `globalThis.process.pid` 会**编译报错**（逼调用方加守卫），而 `globalThis.process?.env` 变成**必需**的写法（当前它恰好是对的，但 TS 不知道为什么）。**

### C4 · 传播半径（盲区 44）：**一处错声明 ⇒ 60 个调用点看不见风险**

`userDir()` 的 **60 个调用点**（`cep/data/*` 17 个文件 · `cep/cloud/*` · `commands/system.ts` · `pages/set` · `pages/style`）
**全部经由同一个 `userDir()`**，而 `userDir()` 的正确性依赖一行 `globalThis.process?.env` ——
**⇒ 这 60 个调用点里，没有一个能看见"无 Node"这个风险**（它们的类型全是 `string`，看起来绝对安全）。
**⇒ 这是"一处声明、六十处盲区"的典型**。
