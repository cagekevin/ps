### D. 超时后果 · 有依据的判断

**D.1 超时后队列与回调（transport.ts:24-69，代码实证）**

- 每个 `evalScriptRaw` 经 `queue.then(...)`（:25）**串行入队**：超时只 reject 当前这条 Promise，**不阻塞队列**（:27 失败也继续）。
- `settled` 标记（:40-56）：超时回调里先 `if (settled) return` 再置 `settled=true`——**超时后若 ExtendScript 后来才回包，`done()` 因 `settled` 已 true 直接 return，回调结果被丢弃**，不会既 reject 又 resolve（避免双重 settle 报错）。**这一步是代码实证的。**
- **推断（标 UNVERIFIED）**：`settled` 只防"同一条"双重 settle；它**不取消已发出的 evalScript**。ExtendScript 单线程一旦开始跑那条脚本，**会跑完**（CEP 的 evalScript 无 abort）。所以"超时=js 端放弃等待，但 PS 端可能已执行完"是从单线程语义推断的，**未真机验证**——但代码层面无法阻止其跑完，故"可能已执行"在逻辑上成立。

**D.2 下一个命令是否塞进同一 ExtendScript 队列**：**会**（实证）。队列是 `transport.ts:16` 的模块级单链，所有 jsxCall 都 `queue.then` 排队（注释 :22「所有调用都会排队，不会并发进入 ExtendScript」）。前一个超时 reject 后，后一个按队列顺序照常 `evalScript`——**前一个若仍在 PS 端跑，后一个会排在它后面**（串行）。即：超时≠前一个停止，后一个仍可能在前一个之后执行。

**D.3 方案（只给标题 + 用户感知 + 代价 + 红线）**

- **A. 超时提示"可能已执行，勿重复操作"**：用户看到带警告的失败文案；代价=文案改动小；不碰运行时验证红线（只读文案）。
- **B. 写类 jsx 超时后自动进"待确认"队列 + 提供查询命令**：用户可事后查 PS 端状态；代价=需新增查询 jsx + UI 态；不碰红线（仍是 jsx 调用，不启运行时自动化）。
- **C. 超时后对该域加短冷却，禁止 2s 内重发同签名写操作**：防重试撞车；代价=需签名去重；不碰红线。

> 三者都不触碰"禁 e2e/浏览器自动化/运行时验证"红线（纯文案与 jsx 调用层面的防御）。

### A. 边界规则 R · 可写进守卫

**A.1 白名单判据选型：按「文件来源 + 导出名清单」（手维护）**

- 选**文件来源 + 显式导出名清单**：守卫静态扫 `import { X } from '@/cep/fs'` 时，先判来源文件（如 `@/cep/fs`、`@/cep/http`），再查该来源文件的「只读导出名清单」是否含 X。清单手维护，但**只列少数确定的只读查询**（userDir/dirUsage/readTextOutcome/readBase64Outcome/extensionDir/combineReads/psScriptsDir 的只读部分），且写函数（writeTextFile*/saveExportedText/removeFile/writeBase64File）**永不进清单**。

**A.3 守卫伪规则（判定步骤）**

```
遇 import 声明 spec 指向 '@/cep/<m>'：
  1. 若 import 带 type 关键字 → 放行（type-only 档）。
  2. 否则若 <m> ∈ {jsx, data, events, transport} → 报错「页面不许 import PS 出口层（含类型）」；fix: 数据走 useCommand+store，类型放 domain。
  3. 否则若 <m> ∈ 白名单来源 {fs, http, env, dialog, open-url}：
       a. 取本 import 的具名绑定 {X}；
       b. 若任一 X ∈ 该来源「写出口清单」{writeTextFile, writeTextFileAtomic, writeBase64File, saveExportedText, removeFile} → 报错「页面不许写入口」；
       c. 否则若 全部 X ∈ 该来源「只读查询清单」→ 放行（记为白名单命中）；
       d. 否则（X 不在任何清单，如 psScriptsDir）→ 报错「未登记的 cep 导出，请先在守卫白名单声明其只读/写属性」。
  4. 其余（cep/types 等无副作用类型来源）→ type-only 已覆盖；值导入非白名单来源 → 报错。
```

报错文案示例：`[boundary] <file>:<line> 页面值导入了 @/cep/fs 的 <X>，属写入口/未登记，请走命令层或先登记只读白名单`。

**A.4 这套规则防不住什么（盲区）**

- `import * as fs from '@/cep/fs'`：命名空间导入，静态难拆出具名绑定，**白名单判据失效**——需守卫额外禁止 `* as` 形式（或解构失败即报）。
- 动态取属性：`const f = require('@/cep/fs'); f.writeTextFile(...)` 或 `fs['writeTextFile']`——字符串索引绕过具名绑定，静态分析看不到；只能靠 AGENTS 约定 + 人工 grep。
- 既读又拼的 `psScriptsDir` 类：白名单若误放进"只读结果"会间接放开 evalScript；必须单列"只读但含宿主调用"子档，页面仍禁。
- 类型与值同名：`import { Foo } from '@/cep/x'`，若 Foo 既导出类型又导出值，type-only 判定靠关键字，漏写 type 即进值分支——需在白名单来源强制"值导入只许只读清单"。
