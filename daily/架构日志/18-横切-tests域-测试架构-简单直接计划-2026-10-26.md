## 13. 继续降复杂度：两次**失败**的实验与终局形态（2026-10-26 夜）

### 13.1 目标

把"桩的生命周期"这套样板（每个装桩文件各写一遍 `afterEach` 卸桩 + 泄漏断言）从测试文件里**收进 helper** —— 复杂度放在该放的地方。

### 13.2 实验一：「文件顶层声明一次，helper 管全部生命周期」⇒ **否决**

试的是 `useHostRequire` / `useHostBridge`（顶层调一次 ⇒ 每例自动装 + 自动卸 + 自动断言）。**两条硬理由让它不成立**（都是现场复算出来的，不是推测）：

1. **多数文件的桩依赖"每例新建的对象"** ⇒ 提到文件顶层就引用不到东西：
   `fs-outcome`（函数内每例新建的 `fs`）· `log-e2e-settings`（同上）· `log-file`（每例新建的 `fakeFs()`）· `style-library-real-fs`（每例才赋值的 `dir`）。
2. **钩子里注册钩子不生效**：`installHostRequire` 若在 `beforeEach` 里被调用，它注册的 `afterEach` **不会生效**（vitest 不允许在钩子执行期间注册钩子）⇒ "helper 收尾"只对"顶层调用"的文件有效 ⇒ 而"顶层装 + 每例卸"对顶层装的文件直接坏掉（第二个用例就没桩了）。
   ⇒ **"每例装"与"每例卸"必须成对出现，不能只搬一半。**

⇒ 这条路**没留下半成品**：全部回退到 §13.4 的终局形态。

### 13.3 实验二：把"泄漏断言"也集中到 helper ⇒ **部分成立**

- **假盘（`installFakeFs`）的 5 个用户：成立** ⇒ 泄漏断言（卸完必须"没有 node"）一次实现、全域生效；探针有效（注释掉卸载 ⇒ 6 个用例红）。
- **真 fs 桩的 13 个文件：不成立**（桩形状每例不同 ⇒ 收尾必须由文件管）⇒ 保留"每文件一个 `afterEach`"。

## 14. 宿主边界收口 + 两个提速实验的阴性结论（2026-10-26 夜，续）

### 14.1 做了什么：宿主边界 7 个入口 → 1 个文件

**触发**：问"测试为什么慢"时发现根因链的第一环是"宿主能力只能靠改 `window` 替换"（见 §14.3）。

| # | 量 | 改前 → 改后 |
|---|---|---|
| 1 | 形状 | `HostDeps { require?, bridge?, cep?, env? }`（三态：`undefined`=没注入读 window · `null`=明确没有 · 值=用它） |

| 3 | 载体 | 生产 1 个文件 `src/cep/host.ts`；测试 1 个文件 `tests/helpers/host-stub.ts` |
| 4 | **入口** | **读点 13 → 0**（`host.ts` 之外）· **写点 2 → 0** · 测试侧写 `window` 的真代码 20+ → 0 |
| 5 | 层数 | 2 层：门（1 文件）→ 使用方（9 模块），无兼职 |
| 6 | N→1 | 宿主边界判据 13 → 5 个 getter，全在 1 个文件 |

**收的 7 类**（判据：*CEP 注入 + jsdom 不提供*）：

| 宿主注入 | 入口 | 原来散在 |
|---|---|---|
| `window.require` / `cep_node.require` | `getRequire()` | `cep/node.ts:43` |
| `window.__adobe_cep__` | `getBridge()` | `paths.ts:51,124` · `transport.ts:10,67` · `events.ts:84` · `build-info.ts:28` |

## 16. 错误的两条通道：日志说原文，UI 说人话

> ⚠️ **这一节归错了卷，已被取代**：同一批改动（含后续的 7 处日志调用、6 处 `catch` 断链、55 处 `reason: string` 根因）
> 的权威记录在 `18-横切-失败表达-调查结论-2026-10-26.md` **§11**。本节留在原处只为不打断本文的上下文，**不要按本节改代码**。

### 16.1 病症

日志里读到的是**人写的文案**，不是系统原文：

```
改前  12:00:00 ERROR [style] 读取样式库失败 CepError: 样式库读不到
改后  12:00:00 ERROR [style] 读取样式库失败 [IO] EPERM: operation not permitted, unlink /u/ku.sj
```

改前那句"样式库读不到"是 **toast 上的用户文案**，被原样抄进了日志 ⇒ 用户报障后仍然要靠猜是 `ENOENT` 还是 `EPERM`。

### 16.2 根因：`CepError` 只有一个文本字段

```ts
class CepError { code; hostCode?; message }   // message 既是"给用户的话"，又被日志当日志文本
```

`describeCepError(e)` = `codeText(code, e.message)` ⇒ 拼成用户文案；`error-handler.ts` 又把它塞进日志主文本 ⇒ 两条通道合成一条。**没有"原始原因"字段**，所以有 3 处把 `e.message` 顶到 `message` 位（`transport.ts:137` / `action-archive.ts:164` / `style-library-io.ts:60`），日志里彻底没有码。

**问题不是"中文有 705 行"，是这 705 行既当 UI 文案又当日志文本。**

### 16.3 改了什么（4 处 + 1 条判据）

| 文件 | 改动 |
|---|---|
| `tsconfig.json` | `target`/`lib` **ES2019 → ES2022**。顺手消除 `tsconfig.json` 与 `tsconfig.tests.json` 的 lib 分歧（同一份 `.ts` 用两套 lib 编译 = 判据分裂）。`useDefineForClassFields` 本来就是 `true`，class 语义不变 |
| `utils/errors.ts` | `CepError` 加第 4 参 `cause`（技术原文）。**自己赋值，不用 `super(msg, { cause })`** —— 那个是 Chrome 93+，CEP 的 Chromium 更老，传了会被静默丢掉 |
| `utils/logger.ts` | 新增 `renderError()`：带 `code` 的按 `[CODE] 原因` 输出、原文不翻译；`cause` 缺时退回 `message`。**一处改，135 处 `log.*` 全部受益** |
| `utils/error-handler.ts` | 日志主文本从 `${source}: ${用户文案}` 改成 `source`（技术原因交给 `oneLine` 从 `code`/`cause` 渲染） |
| `tests/utils/error-channel.test.ts` | **新增 5 条**：cause 进日志含 `EPERM` / message 进 UI 不含 `EPERM` / 无 cause 时退回 message / Node 系统错误走同一渲染 / 无码无 cause 退回 `name: message` |

**探针**：把 `renderError` 的 `cause || e.message` 改回 `e.message`（= 回到"日志只有人话"）⇒ **第 1 条立刻红**（`toContain('EPERM: operation not permitted')` 失败）。已还原。
