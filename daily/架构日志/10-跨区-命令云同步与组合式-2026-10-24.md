## 二、溯源（Phase 1：症状 vs 病根）

- 命令层入口契约基本成立（见 §一）：页面 → `useCommand` → `registry.execute` 单向，无裸调 `execute`、无页面 import `cep/jsx|data|events`（`_probe/index.vue:6` 是唯一例外，那是调试页，非产品页）。
- 病根集中在两处：**① 云同步的「脏信号源」覆盖不全**（5 个同步 unit 只订阅了 2 个的生产者）；**② 命令结果码 `FONT_MISSING` 的消费者只剩「置位 ref」一条路**（`useCommand` 那条分支实为死路，详见 §五 TD-10-20）。
- 这两条都是「生产者改了、消费者不知道」或「消费者绕过入口」的职责错位，符合母体债定义。

## 三、定海（Phase 2：不变式 / 唯一真相源）

- `cloud.pending`（落盘痕迹）与 `cloudSyncQueue` 内存脏集合 `dirty`：**两套语义**（见 §五）。`pending` 是「推失败留下的痕迹」，脏集合是「还没到时间推」。两者不是同一真相源，但 `stores/cloud.ts:14` 把 `queuedUnits`（内存脏）和 `status.pending`（落盘痕迹）并列成「两件事」，页面文案要区分，容易误导。
- `getStatus()` 四数字：`configured`(config)/`ledgerState`(ledger 三态)/`rev/syncedAt/localHash`(ledger 值)/`pending`(pending 落盘)。数据源已分清楚，但 `pending` 与内存 `queuedUnits` 的「两个待办数」会让用户误以为同步引擎自己矛盾（实际是「排队中」vs「历史上没推上去」）。

## 四、切割（Phase 3：深模块 / 真缝隙 / 收敛口）

- 命令层 148 条命令（含 seban 11 条）。`group` 退化成兜底桶（上轮 TD-10-11 已记，本轮复核见 §七）。
- 云同步「触发源」与「同步项」的注册地分两处：`cep/cloud/entries`（5 个 unit 的 read/write 适配）与 `cep/cloud/change-sync.ts`（只订阅 2 个）。新增一个同步项时，适配在 entries 加、但忘了在 change-sync 订阅 → 静默不同步（正是 TD-11-1 的病根）。

### A. M1 分水岭结论（一句话）

**M1 是「延迟同步 + 一条独立的漏推路径」，不是「永久漏同步」，也**不是**「信号生产者缺失」**——三个 repo 全都有 `onChange`；只是 `change-sync` 没订阅。改 `change-sync.ts` 一行组即可修，不动数据层。

#### A.1 打包内容到底怎么来的（决定性）

两条路径**打包口径不同**，这是分水岭：

| 路径                      | 收集函数                                                  | 打包范围                 | 证据                              |
| ------------------------- | --------------------------------------------------------- | ------------------------ | --------------------------------- |
| **手动整包 `upload()`**   | `collectUnits(deps.entries)`                              | **全部 5 个 entries**    | `src/cloud/engine.ts:155`         |
| **后台 `pushUnits(ids)`** | `collectUnitsTolerant(targets)`，`targets` = 传入的 `ids` | **只打 `ids` 里的 unit** | `src/cloud/engine.ts:324,360,365` |

而队列把 `ids` 怎么给的（关键）：`src/cep/cloud/setup.ts:72-77`

```ts
cloudSyncQueue = createSyncQueue({
  async sync(units) {
    const blocked = await gate()
    if (blocked) return blocked
    return engine.pushUnits(units.length > 0 ? units : allSyncUnitIds()) // ← 空集回退全量
  },
})
```

- `markDirty(unit)` 只往内存 `dirty` 集合加；`execute()` 传 `[...dirty]`（`src/cloud/change-sync.ts:127`）。
- 若 `dirty` 非空 → `pushUnits(非空)` → **只推脏集合** → 三个未订阅 unit **不在里头，漏推**。
- 若 `dirty` 为空（启动补偿 / 变可见）→ `pushUnits(allSyncUnitIds())` → **全量 5 个**（`src/cep/cloud/setup.ts:39-41`），三个 unit **顺带被推**。

**结论**：三个未订阅 unit 的本地改动

1. 在「身边有别的 unit 先变脏」的那一轮里 → **不漏也不等**，只是不在这批（它们是等 sweep）；
2. 在「boot / 变可见 sweep」那一轮 → **顺带推上去**（`requestSync` → 空集 → 全量，`src/cloud/auto-sync.ts:38-42` 的 30s 启动补偿 + `onVisibilityChange` 的 `requestSync('visible')`）；
3. 只在「连续编辑、始终有脏、sweep 一直被非空集挡掉」时才长期停推——但 `markDirty` 只是防抖，一旦静默 60s 或有别的 unit 清空，sweep 仍会补上。

所以准确说法是：**「延迟同步（最迟到下一次启动/变可见 sweep）＋ 没有独立触发」**，而不是「关面板即永久漏」(见 E 自查)。用户手点一次「上传」也一定全量带上（A.1 表第一行）。

#### A.2 三个未订阅 unit 各自被谁改、repo 有没有 onChange

| unit            | 用户操作 → 命令                               | 落到的 repo                                   | onChange 能力 | 证据                                                                                                                                                 |
| --------------- | --------------------------------------------- | --------------------------------------------- | ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `font.stars`    | 点星 → `font.rate`（收藏字体，`font.ts:144`） | `starsRepo`（`pick`→`fileRepo`/`memoryRepo`） | **有**        | `src/commands/font.ts:147`；`file-repo.ts:203`、`memory-repo.ts:44`                                                                                  |
| `font.tags`     | 加/删/移标签 → `font.*Tag`                    | `tagsRepo`（同上）                            | **有**        | `src/commands/font.ts:174,190,208,219,289-290`                                                                                                       |
| `font.settings` | 改字体设置 → `fontSet.saveSettings`           | `legacySettingsRepo`（`pick`）                | **有**        | `src/commands/fontSet.ts:444` → `patchFontSetSettings`（`legacy-settings.ts:129-136`，内部 `legacySettingsRepo.update`，emit 在 `file-repo.ts:190`） |

三个 repo 全都有 `onChange`（`file-repo.ts:203-208` 与 `memory-repo.ts:44` 都实现了监听表并在 `emit` 后回调；`pick` 原样透传 `onChange`，`pick.ts:44`）。**所以不是「生产者没提供信号」，是「消费者没订阅」**。

#### A.3 M1 性质判定

- **是「订阅漏了 3 处」还是「信号生产者缺失」？→ 订阅漏了 3 处。** 三个 repo 都有 `onChange`；`src/cep/cloud/change-sync.ts:34-36` 只挂了 `actionIndexRepo`/`actionLibraryRepo`(=`action.library`)、`hierarchyRepo`(=`font.hierarchy`)。修法 = 在该数组补三行订阅 `starsRepo`/`tagsRepo`/`legacySettingsRepo` → 各自 `markDirty` 自己 unit。**不需要改数据层**。
- 附带证据：`change-sync.ts:34-36` 的注释只解释了「为什么是这两类」，**没有说「其余不订阅」是有意的**——即无意的缺口。

#### A.4 pending 不记的后果 + 启动补偿到底读什么

- `pending.record` 只在**推失败/冲突**时写（`engine.ts:381,437,450,463,488`）。三个未订阅 unit 从不 `markDirty` → 从不进 `pushUnits` → **从不写 pending**（推都推不到，谈何失败）。所以用户关面板后，`cloud.pending` **没有这三条痕迹**——这点成立。
- **但启动补偿并不读 pending**。`src/cloud/auto-sync.ts:36-42`：注释明写「**也不读 cloud.pending——pending 是『失败留下的痕迹』，不是触发源**」；实现是 `requestSync('boot')` → `sync([])` → 空集回退 `allSyncUnitIds()` → 全量三方比较。**所以启动补偿走「全量 sweep + 三方比较」，不靠 pending，三个 unit 在 boot sweep 里会被顺带推**（只要 gate 放行、云端可达、云端在 sweep 时确实缺这几条差异）。
- **修正第一轮口径**：不是「靠读 pending 补推」，而是「靠全量 sweep 的三方比较补推」；pending 只是给 UI 看「上次哪几条没推成」。因此 **pending 不记 ≠ 关面板即漏**——漏的唯一条件是「一次 boot/visible sweep 都没发生」（例如开一次、改、直接杀进程且 30s 未到、再没开过）。

### C. M2：FONT_MISSING 全链路（一条链，每步 `文件:行号`）

#### C.1 全链路

1. **产生 code**：`src/commands/fontSet.ts:50` `signalMissingFont(name)` + `:51` `throw new CepError('FONT_MISSING', '字体缺失')`（JSX 结果 `code===1` 时，`:47-52` `requireFontApplied`）。
2. **命令层怎么 return**：命令 `run` 抛 `CepError` → `registry.runWith` 的 `catch`（`registry.ts:121-125`）→ `const code = e instanceof CepError ? e.code : undefined`（`:123`）→ `return { ok:false, reason, code }`（`:125`）。
3. **registry 怎么取 code**：`registry.ts:123` 仅取 `CepError.code`；非 `CepError` 抛出一律 `code=undefined`（`code?: string`，`types.ts:80`）。
4. **useCommand 怎么判**：`src/components/command/useCommand.ts:42` `if (result.ok === false && result.code !== 'FONT_MISSING') feedback.error(...)` → **FONT_MISSING 时不 toast**，静默返回 `false`。
5. **domain 的 Vue ref 怎么被消费**：`fontSet.ts:50` `signalMissingFont(name)` 置 `src/domain/font-missing.ts:7` 的 `missingFont = ref(null)`；页面 `src/pages/fontSet/index.vue:64-65` `missingFontVisible = computed(get: () => missingFont.value !== null)`。
6. **谁真的弹了窗**：**页面自己**——`index.vue:478` `<GModal v-model:visible="missingFontVisible">`，`:483` 文案 `字体「{{ missingFont }}」缺失…`。**弹窗由 `missingFont` ref 驱动，与 `result.code` 无关**（`code` 只用于「别 toast」）。

> 即：**同一事实两条载体**——(`ref` 驱动弹窗) ＋ (`code` 抑制 toast)。两处都成立、都够用，但**彼此不知道对方**：命令只置 ref 时页面弹窗但仍会 toast（除 FONT_MISSING 外其它 code 都 toast）；命令只 throw FONT_MISSING 不置 ref 时不 toast 但**没有弹窗**（静默）。

#### C.2 「code 分支是死路」的证据 —— **推翻第一轮判词：这条分支不是死路，有绿测试，而且测的是真接线**

`tests/commands/free-panel-execute.test.ts:127-137`：

```ts

```

- 用的是**真实 `useCommand`**（非 mock），只 mock 了子命令 `action.call` 抛 FONT_MISSING（`withFailingCommand`，`:74-90` 替换 `run`）。
- 因此 `useCommand.ts:42` 的 `code !== 'FONT_MISSING'` 分支**被真实执行到**，且是绿的。**第一轮「死路」判断错误。**
- 另外 `font-set.test.ts:125-137` 测的是**命令层**：`execute('fontSet.fontName',…)` → 断言 `{ ok:false, code:'FONT_MISSING' }` **且** `missingFont.value==='Missing Font'`。即**ref 与 code 两条载体都被就地断言**。

**真假护栏判定**：这里**不是**「绿测试 + 死代码」。两条载体各有一条绿测试（`free-panel-execute:127` 证 code 分支；`font-set:125` 证 ref+code 同置）。**真正的假护栏在别处**：没有任何一条测试断言「**弹窗出现**」或「**page 消费 code**」——页面 `index.vue` 完全靠 ref，`code` 只有 `useCommand` 一个消费者（抑制 toast）。所以「FONT_MISSING 用户能弹窗」这件事，**在页面侧零测试**（页面无 jsdom 用例验证 `missingFontVisible` 翻转），只有命令侧置 ref 的断言。这是「半条链有护栏、另半条没有」，属 **TD-12-20 的实证补强**（不是新债）。

#### C.3 `as CepErrorCode` 位置 + 实码值对照枚举

- 两处：`src/commands/swatch.ts:47`、`src/commands/freePanel.ts:317`，同为 `new CepError((result.code ?? 'JSX') as CepErrorCode, result.reason)`。
- 枚举成员（`src/utils/errors.ts:9-24`）：`NO_CEP | NO_NODE | TIMEOUT | JSX | PARSE | INIT | IO | NETWORK | NO_SELECTION | FONT_MISSING`（10 个）。
- **实际在用的 code 值**（全仓 `new CepError('<X>'` 去重）：`FONT_MISSING, INIT, IO, JSX, NETWORK, NO_CEP, NO_NODE, PARSE, TIMEOUT`（9 个）。
- 对照：**9 个全部是枚举成员，无一枚举外**。原因：`CommandResult.code` 的唯一生产者是 `registry.ts:123` 的 `e instanceof CepError ? e.code : undefined`，而 `e.code` 类型即 `CepErrorCode` → 运行期不可能出现枚举外的值。
- 所以 `(result.code ?? 'JSX') as CepErrorCode` 是**类型收窄而非语义欺骗**：`CommandResult.code` 声明为宽 `string`（`types.ts:80`）是类型债，但**当前无枚举外实际值被吞**。第一轮把「可能吞」说成「有枚举外码被吞」，**过头了**——现无实证样本（见 E 自查）。
- `NO_SELECTION` 在枚举里但当前 grep 无 `new CepError('NO_SELECTION'` 直接构造——它由 `canRun`/`unmetReason` 那条路径产出（非 code 通道），不影响本结论。

#### C.4 M2 最小收口方向（不让任何一方「再造一份」）

问题本质：**「字体缺失」这一个事实，被生产成两份互不相知的表示**——`missingFont` ref（UI 态，domain 层违规带 Vue）与 `CommandResult.code='FONT_MISSING'`（结果码）。消费者各取一份：页面取 ref、`useCommand` 取 code。

**最小收口 = 让命令结果成为唯一真相，页面不再读 domain ref**：

1. 命令层 `fontSet.ts` 抛的 `CepError('FONT_MISSING')` 里**带上缺失字体名**（`reason` 已有或加结构化字段），删除 `signalMissingFont` 调用；`domain/font-missing.ts` 整个删掉（连带偿还 TD-12-20 的「domain 带 Vue ref」）。
2. 页面 `index.vue` 改为**从 `useCommand` 的返回拿结果**：`useCommand` 目前只 return `boolean`，需要让它把「失败且 code=FONT_MISSING」这一路透出（例如返回 `{ ok, code?, reason? }` 或专门的 `onMissingFont` 回调），页面据 `code` 决定弹窗、据 `reason`/字段取字体名。
3. 于是：`code` 是唯一入口（既抑制 toast 又驱动弹窗），ref 消失。**生产者（命令）出事实，消费者（页面）只转发，谁都不补造。**

#### C.5 交接三句话

1. **先看 `src/cep/cloud/change-sync.ts:12-36` 和 `src/cep/cloud/setup.ts:72-77`**——这两处是云同步"谁触发、推多少"的真相所在，90% 的误解都从这里起。
