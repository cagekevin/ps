## 2. 查项（按优先级，共 31 条：1–18 失败表达 / 19–23 读链 / 24–27 写链 / 28–30 形状重复 / 31 状态词表）

### P0 —— 可能藏着真错（上一个人**完全没查过**）

#### 查 1 · `.vue` 文件一次都没扫过

```bash
grep -rn "status === 'error'\|\.status !== 'ok'\|\.status === 'broken'" --include='*.vue' src
```

**判据**：页面/组件里有没有**没判判别位就取字段**的地方（`x.status !== 'ok'` 之后直接用 `x.reason` / `x.value`）。
**改法**：改成 `x.status === 'error'` 再取失败字段；成功字段必须在 `=== 'ok'` 分支取。
**凭据**：改完该页面测试必绿；把判别位改错应红。

#### 查 2 · `as` 和 `!` 绕过类型（第二条绕过通道，从未扫过）

```bash
grep -rnE "as (RepoRead|CloudOutcome|CommandOutcome|JsxOutcome|ReadFailure|DecodeFail|RepoFileOutcome|SysFontRead|LedgerRead)" --include='*.ts' src
grep -rnE "\)!\." --include='*.ts' src | grep -E "value|failure|reason|list|ledger"
```

**判据**：失败臂上出现 `!`（非空断言）或 `as` ⇒ 等于把"取不到值"这条保证拆了。
**改法**：换成类型谓词收窄（`isRecord` / `isDecodeFail` / 判别位判断）。改不动就在文件头写清为什么必须断言。

#### 查 3 · `catch` 断链（只扫过一轮，之后的改动没再扫）

```bash
grep -rn "catch" -A 8 --include='*.ts' src | grep -B 4 "throw new"
```

**判据**：`catch` 里 `throw new XxxError(...)` 而**没有把原始 error 传下去**（`cause` 第 4 参 / `raw` 字段）。
**改法**：`throw new CepError(code, msg, undefined, error)`；或折成 `{ fail, failure }` 结构。
**注意**：业务判定（"没选分组"）不需要、也不许硬塞 `cause` —— 只有从 `catch` 捕获外部错误时才要。

#### 查 4 · 日志 `detail` 传了"渲染后的一行"而不是观测对象

```bash
grep -rnE "log\.(error|warn|info|debug)\([^;]*describe(ReadFailure|DecodeFail|CepError|CloudFailure)" --include='*.ts' src
```

**判据**：第三个参数是 `describeXxx(...)` 的**返回值**（字符串）⇒ 已经渲染过一道，`field` / `expected` / `errno` 全丢了。
**改法**：传原对象 —— `log.error(scope, '事件描述', decoded)`。
**上一轮已修 2 处**（`events.ts` / `repo-read.ts`），**这条要再扫一遍确认 0 处**。

#### 查 5 · 界面在渲染技术原文（errno / EPERM 直接进 UI）

```bash
grep -rn "\.failure\|\.reason" --include='*.vue' src/pages src/components
grep -rn "\.failure\|\.reason" --include='*.ts' src/pages
```

**判据**：页面文案里出现 `${x.reason}` / `${x.failure...}` ⇒ 技术原文进了用户视野。
**改法**：UI 只要"该做什么"，技术原文进日志。文案归 `msg`；`broken`/失败态说结果 + 下一步，不贴 errno。
**例外**：`reason` 的语义是"给用户看的那句话"时可以用；`failure`（对象）**永远不进 UI**。

#### 查 6 · `ok:` 字段名的残党（只查过 `{ ok: true|false`）

```bash
grep -rnE "\bok: boolean|\bisOk:|success: boolean|\bok\?:" --include='*.ts' src
```

**判据**：还有别的"成没成"字段名 ⇒ 判别位不止 `status`。
**改法**：统一 `status: 'ok' | 'error' | …`；改完跑 typecheck 拿全量清单。

### P1 —— 口径不一致（会诱导下一个人照抄）

#### 查 19 · 有没有人「自己读原文 + 自己 parse」绕过结论层


#### 查 20 · 「读不到」的处置还剩几种

## 2.7 形状重复专项（查 28–30）

> **判据：一个形状 = 一个问题。** 不是「形状数 = 1」（合并不同问题会丢信息），
> 也不是「形状数 = 层数」（一层可以答两个问题：① 既答"成没成"又答"被什么挡住"）。
> 现状 **13 个「成没成」形状 / 10 个问题 ⇒ 欠 3 个**，就是下面三条。

#### 查 28 · `TextRead` 与 `Base64Read` 是同一个形状的两个名字

```bash
grep -rn "TextRead\|Base64Read" --include='*.ts' src
```

**判据**：两者**完全同形**（三臂 `ok` / `notSeen` / `error` 一致，`error` 臂都是 `failure: ReadFailure`），
**只差 `ok` 臂的载荷字段名**（`text` vs `base64`）⇒ 同一个问题，两个名字。

**改法**：合成一个泛型基座

```ts
export type Observation<T> =
  | { status: 'ok'; value: T }
  | { status: 'notSeen' }
  | { status: 'error'; failure: ReadFailure }
export type TextRead   = Observation<string>   // 或直接删掉别名，全仓用 Observation<string>
export type Base64Read = Observation<string>
```

消费点的 `.text` / `.base64` 改 `.value`（约 10 处）。

⚠️ **别顺手改 `RepoFileOutcome.text`** —— 那个 `text` 是**原始文本**（有语义），不是同一个东西。

**凭据**：`tests/cep/fs-outcome.test.ts` · `fs-read-outcome.test.ts` · `fs-remove-base64.test.ts` 三份全绿；
把 `Observation` 的 `value` 改成可选 ⇒ 下游 `x.value!` 要冒出来，说明没堵住。

#### 查 30 · `notSeen` 两种处理（**要先定口径，别直接改**）

#### 查 31 · 失败状态词有 4 个、缺席状态词有 4 个 ← **此前最大的漏点**

```bash
grep -rhoE "status: '[a-zA-Z]+'" --include='*.ts' src | sort | uniq -c | sort -rn
```

**现状（2026-10-26 实测，13 个取值）**：

```
ok 90 · error 78 · absent 17 · notSeen 13 · cancelled 10
unreadable 4 · skipped 3 · none 3 · empty 3 · broken 3 · idle 2 · watching 1 · degraded 1
```

**按"它回答什么"分组**：

| 语义 | 取值 | 数 | 判 |
| --- | --- | --- | --- |
| **失败**（坏了，不能用） | `error` · `unreadable` · `broken` · `degraded` | **4 个词说同一件事** | ❌ 债 |
| **缺席**（没有这个东西） | `absent` · `notSeen` · `none` · `empty` | **4 个词说同一件事** | ❌ 债 |
| 终止 | `cancelled` · `skipped` | 2 | 语义不同（用户取消 / 主动跳过），可留，但要写清区别 |
| 进行中 | `idle` · `watching` | 2 | 状态机，**不是结果**，不算失败表达 |

**改法**：先定两张词表（失败 / 缺席），再逐个映射到各形状。`degraded` 只有 1 处，单独判它到底是"失败"还是"可用但不完整"。

⚠️ **为什么这是最大的漏点**：此前所有统计（"16 个形状""字面量 0 处""自由文本失败 0 处"）
都是按 `grep "status: 'error'"` 数的 ⇒ **`unreadable` / `broken` / `degraded` 这三个失败臂从来没被数过**。
其中 `domain/cloud.ts:253` 的 `CloudPullOutcome` 就是 `{ status: 'unreadable'; reason: string }` —— **自由文本失败，一直躺在那里**。

**凭据**：每映射一处，必须有一处会红的用例；把 `unreadable` 改成 `error` 后，`tests/cloud` 里"回包结构不符必须拒绝写云端"那条应红。

#### B. 「过度收口」的八个动作（都是出于好心）

| 动作 | 听着像 | 实际 |
| --- | --- | --- |
| ① 为消重复**合并两个语义不同的东西** | "一处定义，一处修改" | **最高危**。合并后的类型能表达原有两个，但**消费方拿到的信息少一半**，而且不报错 |
| ② 为零 `\| null` 把**值字段**改成 `Decoded` | "统一失败表达" | 把"这个值是空的"（正常）当成"失败了" |
| ③ 为零字面量给**单生产者**造工厂 | "构造点收口" | 判据是**构造文件数 = 形状数**，不是 0 |
| ④ 为统一名字把**子码并进判别位** | "字段名只留一个" | `{status:'notJson'}` 与 `{status:'error'}` 同形，判别位再也不是"成没成" |
| ⑤ 为"更安全"给失败臂加**可选字段** | "多给点信息" | 两臂合成一臂 ⇒ 下游写哪种都过编译 ⇒ **走回上一轮那个坑** |
| ⑥ 为"补全信息"给**业务判定**塞 `cause` | "错误都要可追溯" | 造假原因，日志里出现一个根本没抛过的错误 |
| ⑦ 为"断言更严"把 `toMatchObject` 全改 `toEqual` | "钉死形状" | 无关字段一变动就红，噪音掩盖真红。**只在"钉死这个形状"时用 `toEqual`** |
| ⑧ 为"收干净"把 `notSeen` 改 `error` | "状态越少越好" | 首次使用 / 文件未生成 = 正常态，改了就报错 |

#### C. 判据：怎么区分「还没收干净」和「本来就该两种」

看**它们回答的是不是同一个问题**：

| 看 | 结论 |
| --- | --- |
| 两个形状 / 两个字段 / 两个函数，**回答同一个问题** | 是债 ⇒ 收 |
| 回答**不同问题**（谁看、哪一层、什么时机） | 是设计 ⇒ **收它就是破坏** |

**说不出区别 ⇒ 是一件事，收**；**一句话能说清区别 ⇒ 是两件事，留着**（并且把这句话写进文件头）。

### 4.8 追问记录：为什么不把失败形状合并成一个？

> 这一节留在这里，因为**上一版的判据是错的**，被追问才改对。留着防重犯。

**上一版写的**：「16 个失败形状不许合并，合并会丢层语义」—— 这是拿**数量多**当理由，站不住。

**数一遍之后**：

| 问题 | 形状 | 数 |
| --- | --- | --- |
| ① 观测成没成 | `TextRead` · `Base64Read` | **2（重复）** |
| ① 观测被什么挡住 | `ReadFailure` | 1 |
| ② 这份数据能不能用 | `RepoReadBad` · `RepoFileOutcome` · `SysFontRead` | **3（重复）** |
| ③ 解析成没成 | `Decoded \| DecodeFail` | 1 |
| ④ 台账 / 云操作 / 云失败原因 | `LedgerRead` · `CloudOutcome` · `CloudFailure` | 3 |
| 宿主 jsx / 命令 / 写盘 / 快速字体 / 预设文本 / 翻译 | 各 1 | 6 |

⇒ **13 个形状，10 个问题，欠 3 个。**

**3 个真重复（该收）**：

1. `Base64Read` 与 `TextRead` **完全同形**，只差载荷字段叫 `base64` 还是 `text` ⇒ 两个名字一件事
2. `RepoFileOutcome` · `SysFontRead` 与 `RepoReadBad` —— 同一个问题，三个名字

**另外 10 个为什么不并成一个**：不是"层不同"，是**状态词表不同**。
`notSeen`（读链）· `skipped` / `cancelled`（云）· `none`（台账）并进一个联合之后，
每个消费方的 `switch` 都要处理自己**不适用**的那几臂 ⇒ 不完备 switch 变多，漏判风险上升。

**顺手发现的一条真债**：`notSeen` 在 `SysFontRead` 里**保留**、在 `RepoRead` 里**折成 `ok + fallback`**
—— 同一个问题，两种处理。

#### 判据修正（这条比上面 4.7 全表都重要）

> **一个形状 = 一个问题。**
>
> 不是「形状数 = 1」（合并不同问题会丢信息），
> 也不是「形状数 = 层数」（**一层可以答两个问题**：① 既答"成没成"又答"被什么挡住"）。

判据是「**同一个问题只许一个形状**」。用这条数：13 → 10。

### 4.9 4.7.A 那张表的复核记录（15 → 11 对 / 3 存疑 / 1 撤回）

> 被追问一句「这 15 项未必都是对的」，复核后有 4 条改了判。**留档的原因：我原来把"现状"当成了"设计"。**

| 原编号 | 原判 | 复核后 | 为什么改判 |
| --- | --- | --- | --- |
| 1 | 16 个形状"不许合并" | **欠 3 个**，13 → 10 | 拿"数量多"当理由，站不住（§4.8） |
| 2 | `kind` 与 `fail` 不同名"是对的" | **⚠️ 存疑** | 两级子码：`fail:'readError'` 下面套 `failure.kind`，而 `kind` 的三个值（`noNode`/`noCep`/`pathEscape`）根本不是"读盘错误"。**说不清它们的关系，就不能叫"对"** |

#### 教训（比表本身重要）

**"现状是对的"这个判断，本身需要证据。** 拿不出证据时，正确写法是 **`⚠️ 待判`**，不是 **"禁区，不许动"**。

- 写成"禁区" ⇒ 挡住了本该收的债（查 31 那个 `unreadable` 就是被我挡了一轮）
- 写成"待判 + 判据" ⇒ 下一个人能自己判

**判据**：说某处"是对的"之前，先回答「**它能被一句话说清和相邻那个的区别吗**」。
说不清 ⇒ 它只是**现存**，不是**正确**。
