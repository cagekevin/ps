**逐对差异证据（差异是真的 vs 没人统一）**：
- StyleMenu vs GPopover：GPopover 已支持 `role=menu`+`useDismiss`+`Teleport`+`matchWidth`（`GPopover.vue:16/73/75`）。StyleMenu 的**唯一真差异**是皮肤（`#363636`/`#3565ff` hover，`:111/:117`）与「分隔线 `separator` 语义」「禁用态 `disabled`」—— 这两点 GPopover 的 slot 内容能表达。其余（定位/关闭/Teleport）GPopover 全有 ⇒ **属于没人统一，不是真差异**。
- style hover 浮层 vs GPopover：**真差异几乎为 0**，只是它没接 `usePopover` 就裸调 `useFloatingPosition`，且**漏了 `useDismiss` 关闭**（hover 浮层可能靠 `v-if` 内容空关闭，但无点空白/Esc 关闭，:1094 无 dismiss 注册）。属「没人统一 + 漏行为」。
- freePanel 菜单 vs GPopover：`position:absolute` 写死 `top:24 right`，**无视口翻转**（窄面板贴右溢出不收）—— GPopover 有翻转。皮肤差异小。**属没人统一**（且 freeze 页但属 bug 类职责错位）。
- FontSetSelect vs GPopover：FontSetSelect 多「搜索过滤 + 重命名/删除行 + sticky 头」，这是**内容能力**非浮层能力；定位用 `absolute`（贴触发下方，不长浮层）—— 可迁 GPopover `matchWidth` 仍保留内容 slot。**属没人统一**。
- DistributedDialog vs CepModal：DistributedDialog 是**输入端弹窗**（带 input + 高级区 + pin 钉住），CepModal 是纯确认。**真差异**：pin 钉住 + 复杂表单。但定位/关闭/遮罩 CepModal 全有，把它当底壳、表单作 slot 即可。属「没人统一」。
- GTooltip：hover 延时 + `pointer-events:none` + 固定 top/bottom 无视口算。**真差异**：纯 hover tooltip，无 trigger 点击。GPopover 是点击触发，不适合取代 hover tooltip ⇒ **GTooltip 应保留独立**，但业务零使用（见 B）。

**统一壳能不能同时服务全部？**
- 能服务：StyleMenu、style hover 浮层、freePanel 菜单、FontSetSelect（浮层部分）—— 全部迁 `GPopover`（`role=menu` 或坐标 ref 版 `usePointPopover`）。
- 必须保留独立：GTooltip（hover 语义与点击浮层根本不同）、CepModal（模态语义）、DistributedDialog 的**表单内容**（壳可复用 CepModal，内容 slot）。

**合并方案（标题 + 受益 + 代价 + 撞冻结页）**：
- **方案 A：浮层壳统一到 GPopover/usePointPopover，皮肤作变量出口**。受益：消除 TD-05-1/2/3 三处重复壳 + GPopover 零接入（TD-05-4）；代价：4 处调用点迁移 + GPopover 加 `separator`/`disabled`/坐标 reference 支持；撞冻结页：/freePanel、/fontSet 若含浮层＝撞冻结——需走「bug/数据错误」口径或新页契约，/style 是新页不受限。
- **方案 B：GPopover 与 GTooltip 二选一弃用其一**。受益：少一个零使用件；代价：hover tooltip 语义需另寻，GPopover 点击触发不适合；撞冻结页：无（均零业务使用）。**建议保留 GTooltip 概念、删 GPopover 或反之**，但业务零使用 ⇒ 先裁决再动。
- **方案 C：组件库文档收敛（M2 检测母体）**。受益：映射表「无重复」改正、横切能力浮层两行补实、`GPopover` 零接入入账；代价：纯文档；撞冻结页：无。

### A. 「三份壳都没做键盘导航」追到底——判定：**范围外（非债）**

1. **到底需不需要**：CEP 面板是鼠标操作的浮动面板（菜单 hover/点击项、hover 描述浮层），三项自造壳（StyleMenu/freePanel菜单/FontSetSelect）与 GPopover **实现侧都没做面板内 ↑↓ 循环/Tab 焦点管理**(`StyleMenu.vue`/`freePanel/FreePanel.vue:362`/`FontSetSelect.vue` grep 0 命中键盘；`usePopover.ts:101-110` 只处理触发键+Esc)。
2. **依据**：① `docs/规范/新控件准入.md:207` 只要求"键盘 Enter/Space 可切换"（针对可切换控件如 GCollapse），**未要求浮层菜单的 ↑↓ 导航**；② 全仓**唯一**实现 ↑↓ 导航的是 `usePopover.ts:106` 的 `ArrowDown`——但那是"触发键打开"，不是"面板内项循环"，且 `SelectBox.vue:29` 复用它走的是下拉项聚焦；③ CepModal 有完整焦点陷阱(`CepModal.vue:40-72` FOCUSABLE+restoreFocus)，**那是模态**（焦点被锁在对话框），与本处"非模态浮动菜单"语义不同，不能外推。
3. **结论**：GPopover 缺面板内键盘导航 = **范围外，不是债**。理由：本仓库的浮动菜单/浮层从未要求键盘项导航（仅模态 CepModal 因焦点锁定才需要），三份壳"都没做"是**一致的共同缺项、且符合本仓控件准入的键盘要求（只到 Enter/Space 切换）**，不是"都没意识到"的遗漏。若将来要做无障碍项导航，那是**新增能力**而非还债；现在不列入 TD。判定硬：**非债，范围外**。

### E. 过程链（用户视角）：同一个操作，两处壳不一样

**现象**：用户在"删东西"这个动作上，有的页弹 180px 方角方块确认（`DistributedDialog`），有的页弹 260px 圆角确认（`CepModal`）——视觉与尺寸都不一致。

1. 用户在 `/fontSet` 点"分发字体"按钮 → 触发 `fontSet/index.vue` 打开 `DistributedDialog.vue`（`fontSet/index.vue` 引用）。
2. `DistributedDialog.vue:103/110` 自绘 `position:fixed` 弹层，宽 `180px`(:113)、圆角 `--r-sm`(:138)、带 pin 钉住 + 高级区 + 回车确认——**完全绕开 `CepModal` 这个全仓确认外壳**（证据 TD-05-2③）。
3. 用户在 `/style` 点"删除分组" → `style/index.vue:765` 调 `CepModal`（经 `v-model:visible prompt`），标准确认框默认宽 `260px`(`CepModal.vue:17/124`)、圆角 `--r-md`(:130)、`aria-modal` 焦点陷阱(:85)。
4. 用户在 `/style` 还能走命令式：`style/index.vue:752` `await confirm.confirm(...)` → `ConfirmHost.vue` 内同样用 `CepModal` 渲染（壳内复用）。
5. 于是"确认"这个动作：在 `/fontSet` 是 180px 方角自绘、在 `/style` 是 260px 圆角 CepModal、在声明式路径又是 CepModal——**三套壳，两种尺寸/圆角**（TD-05-2）。
6. 为什么会两样：没有"确认弹窗唯一生产者"约束，早期 `DistributedDialog` 按"带 input 的复杂确认"自绘、后续页按"简单确认用 CepModal"，命令式 `confirm` 又额外封装一层；三者从未合并（M1 唯一生产者缺位）。
7. 给决定者：若统一，把 `DistributedDialog` 的表单内容作 slot 塞进 `CepModal`（壳统一 260px 圆角），命令式 `confirm` 与声明式 `CepModal` 二选一落 ADR——修 TD-05-2 即可消除 180/260 不一致。

## bug 复核（freePanel 翻转 2026-10-24）

> 只钉 TD-05-5（已落账编号，原 TD-05-2a）。只读，未改代码、未跑债本。

**第 4 问结论（放最前）**：TD-05-5 是 **TD-05-1 的下游症状，非独立债**。根因就是"自造壳没接 `useFloatingPosition`"，迁 GPopover（TD-05-1）后 `computeFloatingPosition` 自带视口 clamp/翻转，bug 自动消失。仅因 freePanel 已冻结、怕 TD-05-1 久拖，才单列 TD-05-5 兜底；TD-05-1 一修即可消。

**1. 具体错在哪**：菜单 CSS `FreePanel.vue:376-386` —— `position:absolute; top:24px; right:var(--sp-1); min-width:132px`，定位容器 `.free-panel__head{position:relative}`(:351-362)。翻转判定侧 = **左侧**（menu 右锚、向左展开，无左边界约束）。对比 `useFloatingPosition` 正确做法差三步：① 没有 `reference.getBoundingClientRect()` 取触发点（freePanel 只 `:95 useDismiss` 做关闭，未调定位）；② 没有垂直翻转 `if (floating.height>below && above>below) vertical='top'`（`floating-position.ts:59-63`）；③ 没有水平 on-screen 约束 `clamp(left, padding, viewport.width-padding-floating.width)`（`:83`），freePanel 用写死的 `top:24px`/`right:2px` 替代 `--floating-y`/`--floating-x`。

**2. 复现场景（纯计算可推）**：freePanel 可拖窄，块容器 `min-width:0`(:447)。设面板宽 W、左缘距视口 X。菜单左缘(视口坐标)= X + (W − 2 − 132) = X + W − 134。当 W<134 即溢出左缘。例 W=120,X=10 → 左缘=−4px，超出视口 4px padding 共 8px；若祖先 `overflow:auto`(:426) 裁剪，菜单左侧 8px+ 被切、对应项点不到。溢出像素 = max(0, 134 − W − X + 4)。窄面板（W≈100–130）必现。

**3. 严重度**：默认宽面板不触发；仅"面板被拖到 <134px 且偏视口左"才溢出，后果是菜单左缘出框/部分被裁剪（非整体跑飞）。属"位置不理想 + 边缘窄面板可能点不到"，**非高频硬崩**。利息率维持**低**（D 表已列低），**不升到高**——不是每次都点不到，且只在窄面板极端态。

**4. 已并入 TD-05-1 关系**：见首段。独立注册只为冻结页兜底，不重复修。
