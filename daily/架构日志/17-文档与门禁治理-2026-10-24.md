## 一、链路快照（refs 实证）

本轮碰的是门禁链本身，不是数据流。`npm run check` 现为 12 步（`package.json` 逐条读）：

```
style:guard → template:guard → assert:guard → dispatch:check → boundary:pages
→ layer:boundary → spec:check → ledger → stats:check → lint → format:check
```

`npm run deploy` = check + typecheck + build + verify:dist —— 与 `ADR-0010`「唯一强制点 = deploy」一致（见 §五 TD-17-2 的裁定）。

## 二、溯源（症状 vs 病根）

三处症状同源：**守卫的判据写在注释里、没写进规则表**。

- `page-boundary.mjs` 头部写「连类型也不行」，但实际漏拦 `@/cep/fs` 的写函数（页面能自己写用户文件），同时把 `import type` 误拦；
- `layer-boundary.mjs` 头部自认「domain 用 Vue / utils 依赖 stores 这两条不在本脚本拦截」——等于**已知方向违规放行**；
- `stats.mjs --check` 只对账不校验口径，通过时却输出得像"数字已验证"。

## 三、定海（不变式）

- 页面层的门禁只有**一条判定链**（三档，按序短路），不再有"注释说一套、规则做一套"。
- 层边界规则集合必须**覆盖文档声明的每条方向判据**；存量可以放行，但必须落在基线里且**只许减**。
- 门禁的输出文案 = 它的**能力边界**：能防什么、防不住什么，通过时就要印出来。

## 四、切割（收敛口）

- 守卫源码是**唯一判据真源**；区域日志只留证据与结论，不再复述规则（避免第二份真相）。
- 基线只承载"存量数字"，不承载"为什么豁免"——理由必须在守卫源码的注释里。

**零炸三问**：

1. **哪些行为被改了？** ① 页面 `import type` 由"被拦"变"放行"（用户可感知 = 开发者摩擦消失，非运行时行为）；② 页面值导入 cep 写函数由"放行"变"拦"（原来能编译过，现在报错——这是**修**，不是改坏）；③ 层边界对 `domain` 引 vue / `utils` 引 stores 由"不拦"变"增量拦"。
2. **改前能走的路径，改后仍能走吗？** 能：现存 4 处页面 cep 导入全绿，`npm run check` 全绿。
3. **改前会失败的，改后仍失败吗？** 仍失败：`import { jsx } from '@/cep/jsx'` 改后照红（`page-boundary.test.ts` 第 4 例）；`domain` 反向依赖 `@/cep` 照红（`layer-boundary.test.ts` 第 4 例）。
4. **本轮自己踩过的零炸失败（必须记）**：第一版 `IMPORT_RE` 为了"不吞下一条语句"把子句限制成单行，结果
   `import {\n  writeTextFile,\n} from '@/cep/fs'` **整条漏拦**——改前能拦（旧正则用 `[\s\S]*?` 跨行）改后拦不住，
   正是零炸禁的"改前能用的改后不能用"。并行轮次（`17-跨区-守卫可证伪`）登记 TD-17-9 点出来后复现并修：
   子句恢复跨行，改用「遇 `;` 或第二个 `import` 即停」约束。`layer-boundary` 同病（TD-17-10），修法是把跨行
   import 压成一条逻辑行后再套原判据。**教训**：改守卫的解析器时，"防误吞"不能靠砍掉合法写法。

**用户可感知的行为变化**：无运行时行为变化（守卫只在构建期跑）。唯一可感知的是 `npm run check` 的输出多两行边界说明。
