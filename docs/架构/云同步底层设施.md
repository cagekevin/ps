# 云同步底层设施 · Plan

> **这不是开发日志。**  
> 本文只描述云同步底层的目标架构、GAS 协议和落地顺序，按 maomao 的现有做法实现。  
> ⚠️ 表示当前未实现、依赖外部确认或存在并发风险。

## 0. 最终决策

| 项 | 决策 |
|---|---|
| 后端 | GAS |
| 账号 | **GAS URL 就是账号** |
| 登录 | 不做 |
| 加密 | 不做 |
| 同步密钥 | 不做 |
| 设备数限制 | 不做 |
| GAS 协议 | 照抄 maomao：`push_data` / `pull_data` |
| 云端结构 | 一份整包快照，不按 record 拆服务端 |
| 冲突模型 | 照抄 maomao：客户端 pull → rev+1 → push |
| 服务端 CAS | 不做 |
| 设备模型 | 主设备 + 临时设备 |
| 临时设备 | 只下载使用，不做双向合并 |
| 冲突粒度 | 整包 rev；后写覆盖先写 |
| 并发保护 | 只做当前进程单飞，不做跨设备/跨进程租约 |
| URL 存放 | `src/config/cloud.ts` 内置；本地 settings 可覆盖 |

URL 是读写凭证，泄露等于数据可被读取和覆盖。

## 1. maomao 的实际做法

maomao 的 `src/components/base/store/cloudSync.ts`：

```ts
CloudSyncEngine.callGateway(action, data)
  → fetch(GAS_URL, {
      method: 'POST',
      headers: { 'Content-Type': 'text/plain;charset=utf-8' },
      body: JSON.stringify({ action, data }),
    })
  → 检查 HTML 权限页
  → JSON.parse
  → 返回 res
```

调用：

```ts
push: callGateway('push_data', dataObj)
pull: callGateway('pull_data')
```

本地：

```
collectLocalData
  → localHash
  → pull
  → normalizeCloudPayload
  → decideUpload
  → push rev+1
  → 写 ledger
```

`autoSync.ts`：

```
首次延迟 30s
间隔 2 小时
离线跳过
后台跳过
内容一致跳过
连续 3 次“稍后”当天退避
```

这就是要抄的部分。

## 1.1 本地是不是横切

是横切，但不能做成“全局云模块直接读所有页面和文件”。

本地采用 **kernel + ports + adapters + composition root**：

```text
页面 / 设置页
  ↓ 只发 cloud.* 命令
commands/cloud.ts
  ↓
cloud kernel（纯编排）
  ├─ snapshot / hash / conflict
  ├─ upload / download
  └─ auto-sync
        ↑ ports
        ├─ TransportPort   ← cep/cloud/gas-transport
        ├─ LedgerPort      ← cep/cloud/file-ledger
        └─ SyncEntryPort[] ← cep/cloud/entries/*
                ↑
        composition root（cloud/setup.ts）
```

硬边界：

1. kernel 不知道 `sj_set.json`、`sj_ztglStar.ini`、动作仓库；
2. kernel 不直接 import `cep/fs-read` / `cep/disk-write` / `cep/jsx` / 页面；
3. 页面不 import `cep/cloud`，只调 `cloud.*` 命令；
4. 每个同步项是 entry adapter，不是 kernel 里的分支；
5. 新增同步项只加 adapter + 在 composition root 注册；
6. 下载写回由 `cloud.download` 命令触发，entry 只走数据层/归档事务，不直接拼路径。

### 本地目录

```text
src/domain/cloud.ts             纯类型 / snapshot / hash / conflict
src/cloud/
  types.ts                      SyncEntry / Transport / Ledger 接口
  engine.ts                     upload / download 编排
  auto-sync.ts                  定时调度
  setup.ts                      composition root
src/cep/cloud/
  gas-transport.ts              push_data / pull_data
  file-ledger.ts                sj_v5_cloud_sync.json
  entries/
    font-stars.ts
    font-tags.ts
    font-settings.ts
```

### 为什么不是每页一套

如果字体、动作、自由面板各写一套：

- 冲突判定重复；
- 台账重复；
- 自动同步重复；
- 错误码和部分失败口径不一致；
- 新页面继续复制。

所以：

- **同步引擎横切**：唯一；
- **entry 适配器纵向**：每个数据源一个；
- **composition root 负责装配**：kernel 不反向依赖业务。

## 1.2 最终形态

最终不是“几个设置的云同步”，而是：

```
用户预设资产同步
  ├─ 字体收藏 / 标签
  ├─ 动作仓库 + 仓库文件
  ├─ 自由面板布局
  ├─ 快捷字体 / 层级预设
  ├─ 颜色 / 渐变 / 字体 / 样式库
  └─ 以后新增的任意预设包
```

特点是：

- 一个同步项可能是多文件；
- 一个同步项可能有依赖顺序；
- 需要 schema 迁移；
- 需要删除/墓碑；
- 偶尔第二台电脑只需要下载使用；
- 不做多设备合并。

所以数据模型需要 unit/file，但不需要 per-unit 云端版本。

### 云包结构

第一版使用内联 unit 结构：

```ts
interface CloudSnapshot {
  type: 'psz_sync'
  schema: 1
  rev: number
  updatedAt: number
  units: Record<string, SyncUnit>
}

type FileContent =
  | {
      kind: 'inline'
      data: string
      encoding: 'json' | 'text' | 'base64'
    }
  // 预留：远程 blob 只定义形状，第一版不实现
  | {
      kind: 'remote'
      sha: string
      size: number
      encoding: 'json' | 'text' | 'base64'
    }

interface SyncUnit {
  schema: number
  hash: string
  files: Array<{
    path: string
    size: number
    content: FileContent
  }>
  deleted?: boolean
}
```

特点：

- 多文件；
- 每个 file 有内容引用；
- 第一版只实现 `kind: 'inline'`；
- 不做 blob store / GC；
- 没有 per-unit rev；
- 没有服务端 CAS；
- 整包 `push_data / pull_data`；
- 删除用 `deleted: true`；
- 迁移用 `unit.schema`。

大文件策略：

- 第一版不做分片/远程 blob；
- 单包超过设定阈值时明确报错，不静默截断；
- 以后真有超大资源再单独设计，不提前引入 blob 生命周期。

### 本地台账

只保留整包状态：

```json
{
  "rev": 3,
  "syncedAt": 1760000000000,
  "localHash": "abc123"
}
```

- 不做 deviceId；
- 不做 per-unit rev；
- 不做跨进程租约；
- 整包冲突判断。

### adapter 接口

不是 `read(): unknown`，而是单位包：

```ts
interface SyncUnitAdapter {
  id: string
  schema: number

  read(): Promise<UnitPayload>
  write(payload: UnitPayload): Promise<WriteOutcome>
}

interface UnitPayload {
  hash: string
  files: Array<{
    path: string
    size: number
    content: FileContent
  }>
  deleted?: boolean
}
```

这样：

- 单文件：`files` 一条；
- 动作仓库：`files` 多条，`write` 走归档事务；
- 大文件：第一版只走 `inline`，超过阈值明确报错；
- 删除：`deleted: true`，不是“文件不存在”；
- `unit.hash` 用于 diff / 跳过 / 部分写回，不用于多端版本。

### GAS 仍然照抄 maomao

传输层仍然：

```
push_data { data: CloudSnapshot }
pull_data
```

服务端仍然只存整包。

也就是说：

- **传输协议抄 maomao**；
- **包内数据模型不抄 maomao 的扁平 data**。

这是为了最终形态，不是为了现在复杂化。

## 2. 我们的 GAS 协议

不新增 `get_heads`、`pull_record`、`push_record`。

只保留 maomao 的两个 action：

```json
{ "action": "push_data", "data": { ...整包... } }
```

```json
{ "action": "pull_data" }
```

### 整包结构

```json
{
  "type": "cloud_config",
  "version": 5,
  "rev": 3,
  "updatedAt": 1760000000000,
  "data": {
    "font.stars": [],
    "font.tags": [],
    "font.settings": {},
    "__meta": {
      "rev": 3,
      "updatedAt": 1760000000000,
      "version": 5
    }
  }
}
```

`__meta` 是 maomao 的兜底：GAS 只回 `data` 时还能取回 rev/updatedAt。

## 3. 回包归一化

照抄 `normalizeCloudPayload`：

```
形态 A：{ data: { ... }, rev, updatedAt }
形态 B：{ ...data, __meta: { rev, updatedAt } }
```

统一成：

```ts
interface CloudSnapshot {
  rev: number
  updatedAt: number
  data: Record<string, unknown>
  hasMeta: boolean
}
```

无有效数据 → `null`。

## 4. 本地台账

文件：

```
sj_v5_cloud_sync.json
```

结构：

```json
{
  "rev": 3,
  "syncedAt": 1760000000000,
  "localHash": "abc123"
}
```

字段与 maomao 的 `SyncLedger` 一致：

- `rev`：上次同步的云端修订号
- `syncedAt`：上次成功同步时间
- `localHash`：上次同步时本地内容指纹

## 5. 内容指纹

照抄：

```ts
stableStringify(data)
  → contentFingerprint
```

用途：

- 本地是否改动；
- 云端内容是否与本地一致；
- 一致则跳过，不产生假冲突。

## 6. 上传冲突判定

照抄 `decideUpload`：

```ts
type UploadConflictKind =
  | 'none'
  | 'cloud-newer'
  | 'both-changed'
  | 'cloud-unknown'
```

规则：

```
无台账                 → 视为 localDirty
云端读不到             → cloud-unknown
云端 hash == 本地 hash → inSync，跳过
云端为空               → none，首次上传
云端有数据、无台账     → cloud-newer，必须问
cloudRev > ledger.rev  → localDirty ? both-changed : cloud-newer
否则                   → none
```

上传：

```
localHash = hash(collect)
cloud = pull + normalize
decision = decideUpload(...)

inSync        → skip
conflict      → onConfirm / onAutoConflict
cancel        → 停止
download      → 交给 downloadConfig
none          → push rev+1
成功          → writeLedger
```

不实现服务端 CAS，和 maomao 一样。

## 7. 下载流程

照抄 `downloadConfig`：

```
pull
  → normalize
  → diffWithLocal(cloud.data, local)
  → 有 conflicts → 列清单确认
  → restoreLocal
  → 重水合 store
  → writeLedger
```

部分失败：

```ts
{ ok: false, partial: { failed: [...] } }
```

不能把部分失败报成完整成功。

## 8. 同步范围登记表

照抄 maomao 的 `STORAGE_KEYS.sync` 思路：

```ts
export interface SyncKeyMeta {
  label: string
  sync: boolean
}

export const SYNC_KEYS: Record<string, SyncKeyMeta> = {
  'font.stars': { label: '字体收藏', sync: true },
  'font.tags': { label: '字体标签', sync: true },
  'font.settings': { label: '字体面板设置', sync: true },
  'font.quick': { label: '快捷字体', sync: true },
  'font.hierarchy': { label: '层级预设', sync: true },
  'free.panel': { label: '自由面板布局', sync: false },
  'action.libraries': { label: '动作仓库', sync: false },
  'ui.prefs': { label: '界面偏好', sync: false },
```

规则：

- 只有 `sync: true` 进云；
- 缺省不同步；
- 新增同步项只改这里 + 对应 adapter；
- GAS 端不需要知道 key。

## 10. 自动同步

照抄 maomao：

```
首次 30s
2 小时一轮
离线跳过
document.hidden 跳过
isSyncing 跳过
连续 3 次“稍后” → 次日 00:00 前退避
只自动上传，不自动下载
```

### 我们多两条约束

```
1. 只有主面板启动自动同步，独立自由面板不启动
2. 没有本地台账、但云端有数据时，禁止自动上传
```

第 2 条是给“临时第二台电脑”用的：

```
新设备首次打开
  → 本地没有 ledger
  → 云端已有数据
  → 不自动 push
  → 提示：云端已有配置，是否下载？
  → 用户下载后才建立 ledger
```

这样第二台电脑可以直接下载使用，  
不会在首次启动时用默认设置覆盖云端。

原因：我们没有 maomao 的共享 localStorage，两个 CEP 面板各自有内存。

**不做跨进程租约。**  
多设备/多窗口并发不是核心场景，冲突模型保持 maomao 的整包后写覆盖。当前进程内只做 `isSyncing` 单飞。

## 14. 测试

- `normalizeCloudPayload` 两种回包；
- `contentFingerprint` 键序无关；
- `decideUpload` 四种 kind；
- 内容一致 skip；
- 云端空首次上传；
- 下载 diff + 取消不写；

## 15. 风险

| 风险 | 处理 |
|---|---|
| URL 泄露 | 视为密码；不日志、不提交；泄露换 URL |
| 多窗口并发覆盖 | 与 maomao 相同，接受后写覆盖；不做跨进程租约 |
| 第二台电脑首次启动覆盖云端 | 无 ledger + 云端有数据时禁止自动上传，先提示下载 |
| 整包较大 | 第一版内联；超阈值明确报错；不静默截断 |
| `sj_set.json` 未知键丢失 | 只 patch 登记字段 |
| 两个面板同时自动同步 | 只主面板启动；进程内单飞 |
| GAS 权限页 HTML | transport 检测 `<html` 并报错 |
