### 0.1 哪个同构、哪个不同构（**别再笼统说"四类同一套容器"**）

| 扩展名 | 顶层结构 | 与 `.kux` 是否同构 |
|---|---|---|
| `.kux`（全库） | `{arrFileData:[…], store:{index,list}}` | — 基准 |
| `.dzx`（动作全库） | `{arrFileData:[…], store:{index,list}}` | ✅ **同构**（只有 `store.list[i]` 的键不同，见 §5） |
| `.kus`（单库） | `[{name,data}, …]` **扁平数组** | ❌ **不同构**，**没有 `arrFileData`、没有 `store`** |
| `.kug`（单库） | `[{name,data}, …]` **扁平数组** | ❌ 不同构（读码 `:52666-52691`，`JSON.stringify(s)` 里 `s` 就是数组） |
| `.kuc`（单库） | `[{name,show,list}]` **组数组本身**（连 `{name,data}` 都不套） | ❌ 不同构 |
| `.kuf`（单库） | `[{name,show,list}]` **组数组本身** | ❌ 不同构 |

**一句话**：**只有 `.kux` 与 `.dzx` 是容器**；`.kus/.kug` 是"扁平 `[{name,data}]` 清单"；
`.kuc/.kuf` 直接就是"组数组"。实现时**必须先判 `Array.isArray(j)`**，不能再无脑读 `j.arrFileData`。

**这几层不是同一层东西**：`.kux`/`.dzx` 是"打包容器"，`.kuc/.kug/.kuf/.kus` 是"单个库的数据文件"。
真正被面板日常读写的**不是**这些扩展名，而是 `%APPDATA%\SheJiZhuLi\` 下的 1 个索引 + N 个库文件（§2）。

## 1. 三层结构总览

```
⑶ 导出物（用户可见扩展名）—— 两种顶层形态，别混
   ⑶a 容器：  .kux（全库）  .dzx（动作全库）
              → { arrFileData:[{name,data:base64}], store:{index,list:[…]} }

   ⑶b 扁平清单： .kus（单库）  .kug（单库）
              → [ {name, data:base64}, {name:"kuStyle/….psd", data:false}, … ]

   ⑶c 裸组数组： .kuc（单库）  .kuf（单库）
              → [ {name,show,list:[…]}, … ]        ← 没有 name/data 包装

⑵ 仓库索引（常驻磁盘；被 ⑶a 的 store 原样内嵌）
   %APPDATA%\SheJiZhuLi\sj_kuStoreInfo.ini   = {index, list:[{name,show?,color,gradient,font,style}]}

⑴ 库数据文件（常驻磁盘；被 ⑶a 的 arrFileData / ⑶b 的 [0] 逐条 base64 内嵌）
   sj_kuCol<ID>.ini|.json   颜色库    = [{name,show,list:[{name,color}]}]
   sj_kuGra<ID>.ini|.json   渐变库    = [{name,show,list:[{name,gradient}]}]
   sj_kuFon<ID>.json|.ini   字体库    = [{name,show,list:[{name,fonts:[…]}]}]
   sj_kuSty<ID>.ini|.json   样式库    = [{name,show,id,list:[{name,id,layerId,…}]}]  ← 项字段只到最小校验集，见 §6
   Gradient/<…>.png         渐变预览图（可选旁路文件）
   kuStyle/<groupId>.psd    样式组缩略图（可选旁路文件）
   kuStyle/<itemId>.png     样式项缩略图（可选旁路文件）
```

**所有层都是 UTF-8 JSON 文本**，没有 zip、没有二进制头、没有专有编码。
**但顶层形态有三种（⑶a/⑶b/⑶c），解析第一条判断必须是 `Array.isArray(JSON.parse(text))`**（§0.1、§2.6）。

### 1.1 三处编码别混写成一种（最容易写错的一段）

这里有 **三套互不相同的字节形态**，产物不同、用途不同、写错就对不上：

| # | 位置 | 字节形态 | 实测依据 |
|---|---|---|---|
| ① | **导出物整体**：`.kux`/`.dzx`（对象）与 `.kus`/`.kug`（数组）、`.kuc`/`.kuf`（裸组数组） | **纯 JSON 文本，UTF-8，无压缩、无 base64** | A/B 首字节 `7b` = `{`；**D 首字节 `5b` = `[`**；`JSON.parse` 都直接成功 |
| ② | **`data` 字段**（`.kux` 的 `arrFileData[i].data` / `.kus`/`.kug` 的 `[i].data`） | **`base64(库文件的 JSON 文本)`** —— 只有一层，**没有 gzip** | A 的 8 条 payload 解出首 4 字节 `5b 7b 22 6e` = `[{"n`，7 条与磁盘文件**字节全等**；D 的 `[0].data` 解出 79 B 与磁盘样式库字节全等 |
| ②′ | **`data` 不是字符串时** | **布尔 `false`**（不是省略、不是 `""`），表示"这个文件当时读不到" | **D 实测**：`{"name":"kuStyle/YS5B2C4C06B1029543.psd","data":false}`；A 第 6 条同形（§2.5、§2.6） |
| ③ | **云端上传体 `sj_cloudSync.json → list[i].fileData`** | **`base64(gzip(base64(磁盘原始字节)))`** —— 两层，外面那层 gzip 是同步通道自己的 | C 的 `fileData` 全部以 `H4sIAAAAAAAA`（gzip 魔数）开头；`gunzip`→内层 base64→decode 后与磁盘文件**字节全等** |

**关系式**（照抄用）：

```
①a = JSON.stringify({ arrFileData: [ { name, data: ② } ], store })   ← .kux / .dzx
①b = JSON.stringify([ { name, data: ② }, { name: "kuStyle/….psd", data: false } ])  ← .kus / .kug
①c = JSON.stringify([ { name, show, list } ])                        ← .kuc / .kuf
②  = base64( UTF8( 库文件内容 ) )                     ← 本地/导出，无 gzip
③  = base64( gzip( base64( 磁盘原始字节 ) ) )          ← 只有云同步，本地文件里永远不出现
```

四条落地约束：
1. **不要把 ③ 写进任何导出文件**。原版 `export` 只调 `readBase64`（`:53459/:53497/:53530` 等），没有 gzip 步骤；
   gzip 只出现在云同步的 `readClientPathBase64`（`:4391-4399`）。产品文档/代码里这两条必须分开表述。
2. **② 的 base64 是否含换行不固定**：B（安装包预设 `.kux`）每 76 字符插 `\n`；A（本机全库 `.kux`）**8 条 payload 全部无换行**；
   **D（本机单库 `.kus`）又带换行**（109 字符里在第 76 位有一个 `\n`）。
   → 三份样本两种形态并存，解码前一律 `strip(/\s/g)`，写盘时不要自己插换行。
3. **`data` 不一定是字符串**：文件读不到时它是布尔 `false`（实测 D 的 `.psd` 项、A 的第 6 条）。
   解码前**必须** `typeof data === 'string'` 判断；直接 `Buffer.from(false,'base64')` 会抛（§2.5、§2.6）。
4. **顶层要判数组**：`Array.isArray(parsed)` 为 `true` 走 ⑶b/⑶c（无 `store`），为 `false` 才是 ⑶a 容器（§0.1）。

### 5.1 `.kux` 与 `.dzx` 是同一套容器（**只限这两者**）

## 7. 落地清单（给实现的人）

按 §3 顺序抄，不要跳层：

1. **IO 原语**：`src/cep/fs.ts` 已有 `readTextSmart / writeTextFile / userDir`；
   **缺** `readBase64 / writeBase64 / b64ToUtf8 / utf8ToB64`（CEP 侧 `cep.fs.readFile(path,"Base64")` 与
   `cep.encoding.convertion`，行号 `:72476-72483`、`:72751-72760`）。先补这一层并加单测。
2. **索引仓库**：`fileRepo('/sj_kuStoreInfo.ini', …)`，类型
   `{index, list:{name, show?, color, gradient, font, style}[]}`；**未知键原样保留**（§2.2）。
3. **四个库仓库**：都是"JSON 数组文件"，用 `fileRepo`。**但导出/导入文件有三种顶层形态，必须先分派**
   （§0.1）：
   ```ts
   const parsed = JSON.parse(text)
   if (!Array.isArray(parsed)) {
     // ⑶a 容器：.kux / .dzx —— parsed.arrFileData / parsed.store
   } else if (parsed[0] && 'data' in parsed[0]) {
     // ⑶b 扁平清单：.kus / .kug —— [0] 是库文件，[1..] 是旁路图（data 可能是 false）
   } else {
     // ⑶c 裸组数组：.kuc / .kuf —— 数组本身就是组数据
   }
   ```
   **这一层分派不能放进 `fileRepo`**（`fileRepo` 只管"读一个 JSON 文件"），否则 `.kuc/.kuf` 会被误当容器。
4. **容器能力**：`encodeContainer(files) / decodeContainer(text) / renameInnerFiles(payload)`，
   一份实现，**只给 `.kux` 与 `.dzx` 用**（§5.1、§5.2）。里面必须实现四条：
   - `decodeBase64Field(v)`：先判 `typeof v === 'string'`；`false`（布尔）→ 视为"文件缺失"，**不抛错、不解码**
     （§2.5 第 3 点、§2.6 第 2 点）。**`Buffer.from(false,'base64')` 会直接抛 TypeError。**
     等价写法（原版 `:53680`）：`if (v == 0 || v == 'false') → 空内容`。
   - 解码前 `v.replace(/\s/g,'')`（换行有无都要吃，§2.4）
   - **只做 base64，不加 gzip**（gzip 是云同步那一层，§1.1）
   - 写回时**不要**把"文件缺失"写成 `""` 或省略，保持 `false`，与原版一致（§2.6 第 2 点）
   - 内层名分派照抄 `:53678-53691`：`sj_kuCol/Sty/Gra/Fon/Fot` 前缀 → 库文件；
     `.png` → `name.split('/')[1]` 去 4 位；`.psd` → 去前缀 2 位 + 去 4 位
5. **命令层**：`commands/style.ts`（导出/导入/追加/发送到仓库），页面只经 `useCommand`。
6. **云同步**：按 §4.3，上线时明确决定"`.kus` 是否同步"；**不要**照抄原版漏掉 style 的行为当成设计。
7. **明确不做**：`.asl`（PS 原生二进制样式库）**不读、不写、不导入导出**（§0.2）。
   面板侧 0 引用，做了就是凭空造一个原版没有的能力。
8. **样式项按开放结构处理**：只依赖 `{name,id,layerId}`（§2.3），其余键**原样保留原样写回**，
   不要按猜测的字段名建 TS 类型（那是 §6.1 #1a 的未验项）。
