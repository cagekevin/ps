## 0. 口径先说清（避免把基线当成"合规"）

- 硬规则 20(a) 要求第三方边界转型**必须写 `// 断言理由：…`**，且写明「无注释即违规」。
  **全仓 `src/` 该注释命中 0 处**（`Select-String` 计数 0）。所以现有 10 处双转型**没有一处**满足条文，
  它们能过 `npm run assert:guard` 只因登记在 `docs/生成/断言基线.json`（8 个文件 / 10 处）。
- 「兜底算不算违规」按 20(b) 判：**静默回退**（无 `degraded`/`error`/`log.warn`/`feedback.error`）= 违规；
  **带可见信号的降级** = 合规，本清单不列（例：`classification-repo.ts:119,123` 的 `degraded`）。
- 风险等级：高 = 已经在真机上造成过「点了没反应」或会让数据静默走错；中 = 有明确错误路径被吃掉；
  低 = 形状可控但仍是消费侧猜测。

## 8. 丙区问题作答

### 8.1 三类各多少？哪类最多？

- ① 双转型 **10 处 / 8 文件**（`as any` 0，`as unknown as` 10；`8c77177` 时为 12/9）
- ② 消费者侧兜底 **27 处 / 12 文件**
- ③ 测试假对象绕过真实接线 **17 处 / 9 文件**
- **② 最多（27）**。理由：`?? []` / `?? ''` / `catch { return [] }` 是写代码时最省事的动作，
  而且它们**不红**——守卫只认双转型，兜底没有任何门禁。

### 8.2 有没有第四类「替生产者捏造信息」？

**有，而且比第一类大一个数量级。** 三条，全部有实证：

1. **单层 `as` 完全不被守卫看**：`src/` 命中 **179 处**（`git grep -nP` 计数）。
   硬规则 20 的表格里「`(payload as { id?: string }).id ?? ''`」正是单层 `as`，
   但 `assertion-guard.mjs:26-29` 的 `RULES` 只匹配 `as any` 与 `as unknown as`。
   → 规矩二覆盖面 ≫ 规矩一的守卫覆盖面。
2. **`tests/` 不在守卫扫描范围**：**18 处 `as unknown as` / 10 个文件**（`tests/data/common-use-repo.test.ts` ×5、
   `tests/cep/fs-atomic.test.ts` ×3、`tests/cep/fs-usage.test.ts` ×2 等），其中 `tests/pages/set-cloud.test.ts:17-18` 是
   `null as unknown as CloudStatus` / `null as unknown as ReturnType<typeof ref<number>>` ——
   **把 `null` 假装成状态对象**，正是「替生产者捏造」。
3. **`any` 类型（不是 `as any`）**：`src/cep/fs.ts:7` `type RequireFn = (id: string) => any`、
   `:23` `nodeRequire<T = any>`，两处靠 `eslint-disable-next-line @typescript-eslint/no-explicit-any` 压着。
   你列的 `!` 非空断言我扫了：**0 处**；`@ts-ignore` / `@ts-expect-error`：**0 处**；
   `eslint-disable`：**3 处**（`fs.ts:6`、`fs.ts:22` 是 `no-explicit-any`，`logger.ts:33` 是 `no-console`）。

### 8.3 反过来考你：基线里哪条错或会误导？

**三条，两条是判错，一条是口径误导。**

1. **`registry.ts`×2 不是第三方边界（判错）。** `src/commands/registry.ts:31,39` 转的是
   **我们自己的** `Command<CommandPayloads[K]>` → `Command<unknown>`，是内部泛型擦除，
   该走「改生产者类型」。所以「8 处真第三方边界」实际是 **6 处**（`fs.ts`×3 / `dialog.ts` /
   `http.ts` / `logger.ts`），内部类由 4 处变 6 处。
   **已被证实**：`d9d5921` 直接把这两处 `as unknown as` 删掉就通过编译与 `assert:guard`——
   真第三方边界删不掉（`window.require` 没有类型就编译不过），能裸删说明它从来不是边界。
2. **「8 处真第三方边界」暗示它们合规（误导）。** 硬规则 20(a) 写「无注释即违规」，
   而全仓 `// 断言理由：` 命中 **0 处**——这 6 处（乃至全部 10 处）按条文**全部违规**，
   只是被 `docs/生成/断言基线.json` 冻结。基线把「欠账」显示成了「余额」。
3. **`commands/commonUse.ts:620` 你判「中」，我判「高」。** 它就是 T-97-8 的同一处：
   `await` 已补上，但 `as unknown as Record<string, unknown>` 还在，
   `readCommonUseOptions().value` 的生产者类型仍没定死。判「中」会让它排在 `transport.ts:118` 之后，
   而它才是**唯一已经上过真机、出过 bug** 的那一处。依据：`src/commands/commonUse.ts:546-556,616-620`
   与 `AGENTS.md:649-651`。

数字本身（12 处 / 9 文件）**在你说的时候是对的**，与 `8c77177` 的 `docs/生成/断言基线.json`
完全一致；`d9d5921` 之后是 **10 处 / 8 文件**。要记住它是**基线数**（只统计没有理由注释的行），
不是「全仓双转型总数」——全仓 `src/` 恰好也是这个数，`tests/` 另有 18 处未计。

1. **违规处数 / 守卫可拦数**——刀 A 那 5 处删完，`docs/生成/断言基线.json` 从 8 文件 / 10 处降到 3 文件 / 5 处，这是**唯一能进 `npm run check`** 的数字；四个度量里没有一个能表达"门禁从红转绿"。若你的"第五个"就是它，那它该进表。
2. **类型检查覆盖面**——转型是把一处表达式的类型检查关掉，`.d.ts` 是把它打开。这件事没有任何分支/真相/猜测的计数能表达：`fs.ts:10` 只降 1 项接口暴露，真正收益是全仓 `window.require` 从此有类型。
3. **失败可发现性（响 / 静默）**——20(b) 的判据是"有没有可见信号"，但"有信号"与"静默"在四个度量里**完全同形**。`font-apply:22` 的空对象该不该算债，靠的是"被调用会不会 TypeError（响的）"，不是任何计数。

再补一条更根本的：这四个度量都是**减法度量**，判不了"该不该存在"。`style-library-io:228` 数字上像兜底，取证后是契约 —— 所以任何度量表都得配一句"取证优先于计数"。
