# ADR-0015 · 数据文件四种形态，全部收口在 `data/`

- **状态**：生效
- **结论**：数据文件四种形态全部收口在 data/，每文件一个 Repo<T>：串行队列 + 原子写 + .bak + onChange 订阅。
- **日期**：2026-10-22（取自源文档状态索引「定于」列，未逐条 git log -S 复核）
- **裁定人**：UNVERIFIED（源文档未记每条裁定人）
- **触发**：20 个数据文件全部来自原面板 $config.path，原面板会同时读写

## 背景

源文档（`docs/架构/决策记录.md`）本条未单列「背景」段：旧约定与原因写在「决定 / 原因 / 由来」字段里，已随「判据」段逐字搬来。

## 判据（它凭什么成立 / 为什么不成立）

- **决定**：持久化只允许出现在 `data/`，按四种形态处理：
  1. 平铺 JSON（`sj_dzStoreInfo.json`、`sj_set.json`）
  2. 子目录多文件（`kuStyle/`、`Gradient/`）
  3. 外部交换（`.dzx`、`.cmm`、样式预设：任意路径 + 文件对话框）
  4. 低容忍高频写（星级、标签、`sj_ztglFrequency.json`、`sj_ztglHistory.json`）
  每个文件一个 `Repo<T>`：per-file 串行队列 + 原子写 + `.bak` 备份 + `onChange` 订阅。
- **原因**：20 个数据文件全部来自原面板 `$config.path`（`app.v4.js:5208-5242`），**原面板会同时读写同一批文件**，所以读只能容错、写必须保守。四种形态的 IO 语义差别很大（目录枚举、任意路径、高频写），不集中收口就会各写一套。
- **实证**：`json-file.ts` 与 `prefs.ts` 是两套读改写实现（一个有备份/原子写，一个没有）；`jsonFile.update` 是裸的 `await read → write`（`json-file.ts:59-65`），连点星级丢更新。
- **代价**：新增数据文件必须先加一行仓库定义，不能"随手 readFileSync 就改"。
- **收口之后还剩一层（ADR-26）**：本条把"读"收进 `data/`，但 `data/` 里仍可绕过读原语直接 `readFileSync` / 各自判"文件在不在"。`data/` 之下还有一道唯一读入口，见 ADR-26。
- **什么时候推翻**：我们完全接管这批文件、原面板不再共存时（可去掉 `.bak` 与部分容错）。
