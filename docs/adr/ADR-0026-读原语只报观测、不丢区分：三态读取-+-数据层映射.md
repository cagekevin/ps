# ADR-0026 · 读原语只报观测、不丢区分：三态读取 + 数据层映射

- **状态**：生效
- **结论**：读原语只报观测不丢区分：不抛但必须带回原因的三态读取，语义映射放数据层，唯一读入口 + 具名例外。
- **日期**：2026-10-23（取自源文档状态索引「定于」列，未逐条 git log -S 复核）
- **裁定人**：UNVERIFIED（源文档未记每条裁定人）
- **触发**：同一原语族里「区分被算出来又被扔掉」发生了两次

## 背景

源文档（`docs/架构/决策记录.md`）本条未单列「背景」段：旧约定与原因写在「决定 / 原因 / 由来」字段里，已随「判据」段逐字搬来。

## 判据（它凭什么成立 / 为什么不成立）

- **决定（判据）**：
  1. **错误模型：读不抛，但必须带回原因。** 读失败是常态（首次使用、文件被 PS 占用、同步盘没挂），不是异常。改成 `throw` 会逼每个调用点写 `try/catch`，而 `catch` 的默认写法就是 `return null` / `return []`——**只是把丢信息的地方从原语挪到调用点**。所以：不抛；返回值**不许**是 `string | null`，必须是一个带原因的形状。
  2. **原语只报观测，不报结论。** 原语报告"在那个路径上看不到文件内容"以及**为什么看不到**（读抛错就带原始错误码与文本）；原语**不许**把它翻译成用户可见结论（"首次使用""文件坏了""可以给默认值""必须拒绝写"）。这类结论由数据层按各自语义下：同一个观测，`classification-repo` 判成正常空数据，`legacy-settings` 判成错误。
     - **`notSeen` 必须靠错误码判，不许靠 `existsSync`。** 只认 `ENOENT`；`EPERM` / `EACCES` / `EBUSY` / 网络盘错误**一律 `error`**。依据是实测：本机 `C:\Windows\System32\config\SAM` 存在但不可读，`accessSync` 报 `EPERM`，而 `existsSync` 报 `false`——用 `existsSync` 判存在性，会把"读不到"错判成"没有"，`update` 照样覆盖（T-108 的缝）。
     - **取哪个错误码**：用 `readFileSync` 自己抛的 `code`，不要先 `accessSync` 再读。两者码值相同，但后者多一次系统调用，且"判完到读之间文件变了"是一个真实的窗口（TOCTOU）。
     - **精度上限（已知残差）**：ExtendScript 的 `File.exists` 没有错误码，权限与不存在都返回 false。有 Node 时不影响结论（`combineReads` 让 Node 的 `error` 压过 jsx 的 `notSeen`）；只有 CEP 没开 `--enable-nodejs` 时才退化成不精确。
  3. **每层用自己的词汇，映射放在边界。** `fs.ts` 给自己的三态形状，`data/` 给 `RepoRead`；**`fs.ts` 不许 import `RepoRead`**（那是四层反向依赖，`cep/` 不该知道仓库层契约）。映射只发生在一个地方：数据层接原语的那个函数。
  4. **一个判据，两个读入口。**（**2026-10-25 修订**：原文写的是"唯一读入口 + 具名例外只有一个：同步 CAS 比对"，与实际不符 —— 同步读函数的消费者是两个，不是例外一个。）
     - **同步入口 `readTextSync`**（Node-only 快路径）。消费者**三个**（`grep -rn "readTextSync(" src` = 3）：① `file-repo` 的 CAS 比对（落盘前"原文是不是这段"，D-26 硬需求）；② `settings` 的同步偏好链（`getPref` 在 store 顶层 ref / `computed` 里不能 `await`）；③ `log-file` 的 dump。
     - **异步入口 `readTextAsync`**（Node 优先 + jsx `File` 回退）。
     - **判据只有一份**：两者共用 `readTextNode` + `classifyFsError`（只认 `ENOENT` 是 `notSeen`）。所以"唯一"在**判据层**成立，在**函数层**不成立 —— 别再把它简写成"唯一读入口"。
     - **各自为什么唯一**：同步——CEP 里能同步读文件的只有 Node `readFileSync`，jsx 是回调式，做不出第二个同步入口；异步——两条路的合并策略只有一个正确位置（`combineReads`），拆开就散。
     - **为什么不能只留一个**：只留异步，CAS 会多一个 microtask 边界（D-26 丢更新处）、`getPref` 无处 await；只留同步，未开 `--enable-nodejs` 时读不到任何文件。
     - 上层（`data/` / `commands/` / `stores/`）只能经**这两个**函数拿文件内容，不许绕到更底层用 `nodeRequire('fs')` 各自读"。
  5. **写路径的前置条件是"读到过真数据"，不是"read 没报错"。** D-42 的判据写成后者时，只要有任何一态被伪装成"没报错"，写就会穿过去。前置条件必须是**可判的**：读到过真实内容（或明确判定为"文件不存在"且该仓库允许首次建文件），否则拒绝写。

- **由来（实证）**：
  > 同一个原语族里，**区分被算出来又被扔掉，发生了两次**：`readTextFile` 的 `existsSync` 与 `catch` 是两个不同原因，都 `return null`；`readTextViaJsx` 的 jsx 脚本里「文件不存在」与 `e.message` 是两个不同字符串，一行 `startsWith → null` 合并掉。**这不是某处写错，是原语的形状允许扔。** 写原语的人默认"调用方不关心原因"——这条偏见要被点名。

  - **两次都是"先算后扔"，不是"没算"。** `readTextFile`（`fs.ts`）先 `existsSync` 再 `readFileSync`，两条分支的信息都在手里，然后一起 `return null`；`readTextViaJsx` 的脚本自己拼了 `ERR_PREFIX + '文件不存在: '`，解析处却只判 `startsWith(ERR_PREFIX)`。**信息不是缺失，是被原语的返回类型裁掉了**——`string | null` 装不下三种状态。
  - **后果不是"日志少一行"，是 D-42 整个失效。** 读不到被压成 `null` → `file-repo` 的 `if (!text)` 走"文件不存在"分支 → `ok: true` + `fallback()` → `update` 里 `if (!read.ok)` 不触发 → 拿 fallback 派生的值覆盖用户文件；而且因为"原文为空"，`.bak` 也不写（`.bak` 只在 `previous` 非空时写）。一次点击，用户资产变成默认值，且没有备份。
  - **为什么 `throw` 不是解**：`readTextSmart` 现在**从不抛**（两条路都自带 `catch`），所以 `file-repo` 里那个 `catch` 是**不可达的死代码**——它给了"读失败会被标记"的错觉，实际一次都没跑过。把原语改成抛，只是让这个 catch 变成可达，而它的内容本来就是 `return { ok:false }`：**同样的信息，换个地方接**。真正缺的是"不抛也能带原因"的返回形状。
  - **测试侧同一病症**：`tests/data/repo.test.ts` 与 `common-use-repo.test.ts` 里"读取失败时 update 拒绝写"的用例，是靠**假 fs 抛错**才绿的——真实原语从不抛，那条用例守的是一条不存在的路径（硬规则 20 判据 2「注入假对象绕过真实接线」的同一形态）。**用例绿 ≠ 路径在。**

- **什么算违规**（每条都标了它违反上面哪一条判据，5 条判据**每条至少一行**）：

  | 判据 | 写法 | 判定 | 为什么 |
  |---|---|---|---|
  | ① | 原语返回 `string \| null`（或 `Buffer \| null`）给写路径用 | 违规 | 三种状态装不下，调用方只能猜 |
  | ① | `catch { return null }` / `catch { return [] }` | 违规 | 原因被扔；ADR-14 扩展二已禁，本条给出它在读层的具体形态 |
  | ② | 原语里判"这算不算首次使用 / 要不要拒绝写" | 违规 | 结论属于数据层；原语只报观测与原因 |
  | ② | 用 `existsSync === false` 判"文件不存在" | 违规 | 它对"存在但读不到"也返回 `false`（实测 `EPERM` 的 SAM 文件）→ 权限问题被当成首次使用 → 写路径覆盖用户文件（T-108） |
  | ② | 把 `EPERM` / `EACCES` / `EBUSY` 归进 `notSeen` | 违规 | `notSeen` 只许由 `ENOENT` 产生；其余必须 `error` |
  | ③ | `fs.ts` import `RepoRead` / `@/cep/data/*` | 违规 | 四层反向依赖 |
  | ④ | 上层（`data/` 之外）自己 `readFileSync` / 调更底层读函数 | 违规 | 绕开唯一读入口，判据就无处落地 |
  | ⑤ | **写路径前置条件写成 `!read.ok`（或 `read.reason` 非空即放行）** | 违规 | 判据 ⑤ 要的是"读到过真数据"；`!read.ok` 只证明"没报错"，任何一态被伪装成"没报错"就穿过去——D-42 原先就是这么失效的 |
  | ⑤ | 写路径前置条件写成"读到过真数据"（或明确 `notSeen` 且该仓库允许首次建文件） | 合规 | 可判、可测 |
  | — | 原语返回 `{ status, reason }`，数据层映射成 `RepoRead`（`ok:true` / `ok:false` + `fallback`） | 合规 | 观测在原语、语义在数据层 |
  | — | 同步 CAS 比对用两态同步读 | 合规 | 具名例外：它只判"等不等"，不判"为什么不等" |

- **代价**：
  - **多一层映射**。数据层接原语的函数要把三态翻成 `RepoRead`，这层不能省——省掉就是让上层直接吃原语形状，等于把 `fs.ts` 的词泄进 `data/`。
  - **每个仓库要自己决定 `notSeen` 的后果**。这是有意的不一致：`classification` 判正常、`legacy-settings` 判错误，**不许为了统一把它收成一条规则**（那正是本条 2 要防的）。
  - **已有调用点不会自动合规**。原语加了三态不等于上层都改用它；没收口的调用点仍然两态，仍然在丢原因。收口是一件事，判据是另一件事，别把"写了 ADR"当成"已经收口"。
